# Orbit V0.0.5 — Studio Terrain Validation Scaffold

Status: **Implementation in progress — M00–M11 complete; M12 next**

V0.0.5 is the first release whose primary purpose is to make the V0.0.4 physical-terrain stack directly usable and testable inside Orbit Studio.

It is not a new terrain-algorithm release. The backend authority contracts frozen by V0.0.4 remain authoritative.

The release succeeds when a developer can create a rocky planet, fly to its surface, edit terrain/biome/process authority from Studio, watch the production terrain regenerate in-place, inspect why it changed, save/reopen the project, and obtain the same physical result without using the sandbox or a second preview implementation.

## Release outcome

From a clean Orbit Studio project, the following workflow must be possible without external asset editing:

1. create/open a project and world;
2. create a rocky planet with a Terrain Surface;
3. select that body and see the **real production terrain** in a Studio Perspective viewport;
4. move from orbital scale to ground scale with a normal editor camera;
5. edit base relief and see bounded deterministic regeneration;
6. author a canyon/terrain constraint directly from the viewport;
7. edit a biome and paint a local override directly on the planet;
8. edit supported terrain-process configuration;
9. inspect dirty/rebuilding/ready state, revisions, cache reuse and M29 fields;
10. save, close and reopen the world;
11. see the authored state reconstruct the same terrain while derived cache/runtime state regenerates;
12. run a scripted editor acceptance sequence that verifies the same path used by the interactive UI.

## Frozen architecture rules

These rules are release contracts and must not be weakened to make the editor easier to implement.

- **One terrain authority.** Studio never owns a second terrain height/material representation. M08 physical material columns and the V0.0.4 authored semantic/constraint inputs remain the authority chain.
- **Production rendering only.** A Studio terrain viewport must consume the same physical terrain streaming/rendering path intended for the game. A simplified editor-only terrain generator is prohibited.
- **Render clipmaps are presentation.** Viewport/camera/clipmap state may select residency and presentation but may not affect physical terrain identity or process results.
- **Semantic authoring only.** Persistent edits must pass through ObjectStore/CommandService or the existing authored terrain asset contracts. UI widgets may not write derived cache/process state.
- **Dependency-driven regeneration.** Authoring changes invalidate only the M27 dependency descendants and bounded spatial scope they actually affect.
- **No UI-thread terrain solve.** Expensive terrain/process generation must be scheduled asynchronously through the existing job/GPU paths. Studio remains responsive while pages rebuild.
- **Explicit live state.** Dirty, queued, building, ready, failed, cache-hit and stale-revision states must be inspectable. Silent background regeneration is not accepted.
- **Generation-safe bindings.** Project/world/universe switches invalidate retained runtime references through the existing StudioRuntimeSnapshot/session-generation contracts.
- **Save authored state, regenerate derived state.** GPU cache contents, transient solvers and rendered debug textures are never serialized as world authority.
- **Editor path equals test path.** Automated V0.0.5 editor acceptance must exercise the same session/model/runtime services used by the UI.

## Primary modules

V0.0.5 should extend existing modules rather than create a parallel editor:

- `editor_model` — semantic terrain/body/process authoring models and commands;
- `editor_session` — authoritative world composition and rebuild boundary;
- `studio_session` — generation-safe runtime binding, terrain viewport/session state and live status;
- `studio_ui` — Surface Authoring, viewport controls, terrain status/debug presentation;
- `surface_model` — per-body `TerrainBodyServices` runtime service ownership;
- V0.0.4 terrain modules — stream/cache/dependency/debug/process/render implementations;
- `render_view` / render graph / RHI — actual Studio GPU viewport resources.

No new scripting language or editor-only scene graph is planned for V0.0.5.

# Milestones

## M00 — Freeze V0.0.5 Studio terrain contracts

Freeze the release boundary before implementation.

Required contracts:

- production-terrain-only viewport;
- semantic authoring boundary;
- generation-safe Studio runtime binding;
- dependency-only rebuild;
- async regeneration;
- persistent authored state / transient derived state;
- editor acceptance through real services.

Acceptance:

- this specification and progress ledger exist;
- every later milestone has a defined ownership boundary and acceptance condition;
- V0.0.4 authority invariants are referenced rather than reimplemented.

## M01 — Live world/surface composition refresh

Close the current semantic-edit → runtime-composition gap.

Today `StudioRuntimeBinding::Refresh()` reaches `StudioSession::Tick()`, but the Studio tick must explicitly synchronize `EditorWorldSession::RefreshUniverseIfChanged()` before active-body/viewport consumers observe the frame.

Implement:

- semantic revision detection during Studio tick;
- universe/surface rebuild before dependent bindings refresh;
- result flags in `StudioTickResult` / `StudioRuntimeSnapshot`;
- exact generation changes when body/surface runtime state is replaced;
- no generation bump for a frame with no semantic changes.

Acceptance:

- editing terrain relief/biome/body properties in Studio becomes visible to `SurfaceComposition` on the next refresh;
- unchanged frames do not rebuild;
- stale runtime snapshots are rejected;
- project/world switches remain transactional.

## M02 — One-command rocky planet creation

Make a test planet trivial to create.

Add an editor command/model workflow such as **Create Rocky Planet** that atomically creates:

- Celestial System if needed;
- Celestial Body;
- Terrain Surface child;
- sensible spherical radius/mass/rotation defaults;
- default terrain recipe;
- automatic `TerrainBodyServices`;
- BaseBiome through composition;
- selection/active-body focus.

The command must be undoable as one authoring transaction.

Acceptance:

- from an empty World, one action produces a valid terrain-bearing rocky body;
- Explorer/Inspector show the semantic objects;
- runtime BodyId and terrain capability appear after the next Studio refresh;
- undo removes the complete created hierarchy.

## M03 — Studio production-terrain runtime bridge

Introduce the world/session-side bridge between an active terrain-bearing body and the production terrain streaming/rendering stack.

It owns **derived runtime presentation state only**:

- active physical terrain body binding;
- observer/camera physical position;
- clipmap tracker/toroidal residency;
- terrain page/region streaming;
- M26 cache access from the body's `TerrainBodyServices`;
- dependency/revision identity;
- live M29 debug-page publication.

It must rebind on `universeGeneration` and active-body changes.

Acceptance:

- no body selected → no terrain runtime;
- terrain body selected → exactly one current runtime binding per viewport/body;
- body/world/project replacement destroys stale streaming state;
- physical page identity is unchanged by viewport recreation.

## M04 — Real terrain in Studio Perspective viewport

Replace the terrain-bearing body's spherical `BodyPreviewRenderer` presentation with the production terrain renderer/stream.

Rules:

- Perspective mode on a terrain-bearing body renders production terrain;
- non-terrain bodies may retain BodyPreview;
- Body Map may initially remain coarse/body-oriented;
- Debug mode remains M29 field presentation;
- no sandbox renderer may be copied into Studio as a second authority path—shared production components must be extracted/reused where necessary.

Acceptance:

- orbit-scale view shows the terrain planet;
- descending toward the surface transitions through production terrain LODs;
- the same physical page/cache identities are visible in Studio diagnostics;
- resizing/docking viewports does not regenerate physical terrain.

## M05 — Planet-to-ground editor navigation

Make the terrain actually inspectable.

Implement editor navigation for the production terrain viewport:

- orbit/focus selected body;
- double-click/focus selected surface point;
- WASD + mouse free-flight;
- configurable movement speed;
- altitude-aware speed scaling;
- fast orbital travel and fine ground movement;
- surface-safe near/far clip management;
- floating-origin/rebase-compatible camera state;
- reset/focus shortcuts.

Acceptance:

- continuous navigation from orbital view to metre-scale terrain;
- no precision collapse at ground scale;
- camera movement alone never increments physical terrain revisions;
- clipmap shifts/rebases remain presentation/residency events.

## M06 — Live terrain rebuild scheduler and status

Provide the editor-facing regeneration controller.

Required states:

- Clean;
- Dirty;
- Queued;
- Building CPU;
- Building GPU;
- Uploading;
- Ready;
- Failed;
- Stale/replaced.

Features:

- edit debounce/coalescing for sliders;
- bounded per-frame generation budget;
- obsolete revision cancellation/rejection;
- page-level and body-level progress;
- manual **Rebuild Dirty** action;
- optional **Pause Regeneration** for inspection;
- deterministic latest-revision wins.

Acceptance:

- dragging a relief control cannot enqueue unbounded obsolete builds;
- UI frame remains responsive during rebuild;
- only dirty M27 descendants regenerate;
- stale completed work is never committed over a newer revision.

## M07 — Terrain service/status inspector

Expose the new V0.0.4 per-body service ownership in Studio.

Show, at minimum:

- active BodyId / semantic terrain object;
- current authority revisions;
- default/exposed geological material identity;
- process-service configuration summary;
- BaseBiome + optional biome count;
- M26 resident pages/bytes, hits, misses, evictions;
- current dirty/building page counts;
- selected physical page/LOD;
- last regeneration reason.

This panel is diagnostic and does not become authority.

Acceptance:

- selecting a rocky body immediately shows its real `TerrainBodyServices`;
- cache counters match M26;
- semantic edit revision changes are visible;
- save/reopen shows fresh derived cache residency.

## M08 — Surface picking and world-space authoring interaction

Add a shared production planet-surface picking contract for Studio viewports.

Return:

- body;
- canonical unit direction / `PlanetSurfacePosition`;
- approximate rendered/physical hit elevation;
- physical page address/LOD when available;
- viewport ray provenance.

Use the same picking seam for:

- selection;
- debug physical-page selection;
- biome painting;
- constraint placement;
- future path/road surface tools.

Acceptance:

- clicking visible terrain returns the expected body-space location;
- picking across cube-face seams is continuous;
- resize/camera mode changes do not alter canonical picked identity for the same ray/surface hit.

## M09 — Direct authored terrain constraints

Bring M04 into normal Studio authoring.

Support initial high-value tools:

- height brush;
- protection brush;
- drainage-guidance brush;
- spline canyon/valley;
- spline ridge/embankment;
- material/geology override.

Requirements:

- viewport placement through M08 picking;
- control-point/gizmo visualization;
- numeric Inspector editing;
- one CommandService transaction per committed gesture;
- undo/redo;
- stable constraint IDs;
- persistence using the existing M04 authority contract or a canonical semantic bridge to it;
- bounded M27 invalidation.

Acceptance:

- draw a canyon in the viewport;
- M09/M10 respond after rebuild;
- undo restores the previous physical result;
- save/reopen preserves the authored canyon and regenerates it identically.

## M10 — Biome paint/edit workflow in viewport

Replace manual unit-direction entry as the ordinary biome workflow.

Implement:

- click/brush local authored biome masks;
- brush radius/strength/opacity controls;
- Add/Subtract/Replace modes;
- live preview footprint;
- optional automatic-placement overlay;
- selected biome color/weight inspection;
- undo/redo and save/reopen.

The underlying M20 authored masks remain authority.

Acceptance:

- painting changes only the intended body-space region;
- M21/M22 regenerate only downstream products;
- scatter visibly follows updated resolved weights;
- automatic placement remains unchanged outside the authored mask.

## M11 — Process configuration authoring

Turn the implemented terrain process services into editable semantic configuration rather than hard-coded runtime defaults.

Provide authored per-body/process records for supported V0.0.4 process controls, beginning with:

- stream power;
- hydraulic;
- thermal/gravity;
- aeolian;
- glacial;
- river/meander;
- coastal.

UI should expose a curated ordinary set plus an Advanced section for exact solver fields.

Rules:

- semantic records own settings;
- `TerrainBodyServices` composes runtime configs from those records;
- changing one process increments only the appropriate revision domain;
- process enable/disable is explicit and deterministic.

Acceptance:

- changing aeolian settings does not rebuild geology;
- changing hydraulic settings invalidates its physical descendants;
- defaults round-trip through save/reopen;
- invalid values are rejected before runtime dispatch.

## M12 — Live physical-page production and M29 integration

Connect the production terrain runtime to `StudioSession::TerrainDebugPages()`.

For resident/recently solved pages publish all available M29 fields with:

- physical address;
- physical LOD;
- authority revisions;
- cache residency;
- invalidation revision;
- seam-compatible neighboring page provenance.

Acceptance:

- Debug viewport can inspect a page produced by the same runtime visible in Perspective;
- all available V0.0.4 fields update after an edit;
- old-revision pages are visibly stale/unavailable rather than silently reused;
- seam overlay operates on neighboring live pages.

## M13 — Editor overlays for terrain cause/effect

Add lightweight overlays to make validation fast:

- dirty page bounds;
- building/uploading pages;
- physical LOD;
- clipmap/residency rings;
- cache hit/miss indication;
- authored constraint extents/control points;
- biome resolved-weight overlay;
- process masks;
- drainage/river vectors where available.

Overlays are presentation only.

Acceptance:

- each overlay can be toggled independently;
- overlay changes never affect terrain identity or regeneration;
- a screenshot can identify why a page changed.

## M14 — Save/close/reopen interactive equivalence

Make persistence validation part of Studio, not only a test executable.

Implement a developer action **Save, Reopen & Verify Terrain** that:

- checkpoints project/world;
- records stable authored/runtime fingerprints required for comparison;
- closes/reopens through `StudioWorkspace`/`StudioSession`;
- verifies semantic IDs and authored revisions;
- confirms derived cache is fresh/empty where expected;
- regenerates selected comparison pages;
- reports equivalence/mismatch without mutating authority.

Acceptance:

- successful round trip reports equivalent authored state and regenerated terrain;
- stale derived cache is not serialized;
- failure identifies the mismatching authority/product.

## M15 — Studio terrain validation scenario

Add a deterministic, editor-driven scenario that can be run manually or by test automation.

Scenario:

1. create project/world;
2. create rocky planet;
3. open production Perspective terrain view;
4. focus a chosen body-space test region;
5. change base relief;
6. author a canyon spline;
7. paint a biome override;
8. change one process setting;
9. wait for current revision to reach Ready;
10. inspect selected M29 fields and cache telemetry;

12. regenerate the region;
13. verify equivalent authority/result fingerprints.

Acceptance:

- the scenario uses the same Studio session/model/runtime services as the real UI;
- no direct test-only terrain mutation is allowed;
- a structured pass/fail report is emitted.

## M16 — Interactive performance and responsiveness diagnostics

Capture editor-facing measurements during the M15 scenario:

- UI/frame CPU time while regeneration is active;
- terrain generation GPU timings already exposed by M30;
- number of queued/obsolete/cancelled pages;
- time from committed edit to selected region Ready;
- cache hit rate while stationary;
- persistent/transient terrain memory;
- draw calls / uploaded bytes for the terrain viewport.

These are diagnostic records first, not hardware-independent CI thresholds.

Acceptance:

- no unbounded queue growth;
- stationary editor view converges to cache reuse;
- the report names GPU/CPU/build configuration and source commit.

Create dedicated deterministic/Studio integration targets covering:

V0.0.5 closes only when the real Orbit Studio workflow passes:

- clean project → rocky planet;
- production terrain visible in Perspective;
- orbit-to-ground navigation;
- relief edit;

# Recommended implementation order

The order is mandatory where dependencies are architectural:

`M00 → M01 → M02 → M03 → M04 → M05 → M06 → M07 → M08 → M09 → M10 → M11 → M12 → M13 → M14 → M15 → M16 → M17 → M18`.

M09–M11 may be developed in parallel only after M08 picking and M06 regeneration scheduling are stable.

M12 depends on M03/M06 because live debug pages must come from the real production runtime.

M15 must not be implemented as a fake scripted backend shortcut; it must drive the same world/session/model services used by Studio.

# Explicit non-goals

V0.0.5 does **not** include:

- a new terrain-generation algorithm family;
- replacement of V0.0.4 physical terrain contracts;
- gameplay/NPC systems;
- vehicle physics;
- final road/spline infrastructure beyond what is necessary for terrain-constraint authoring;
- production asset marketplace/material browser expansion;
- multiplayer authoring;
- a second editor-only terrain renderer;
- path tracing/DLSS work unrelated to testing the terrain workflow.

Those remain later releases once the Studio terrain loop is reliable.
