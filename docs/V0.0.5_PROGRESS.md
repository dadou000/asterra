## First implementation batch

After V0.0.4 completes, start with these three milestones together:

1. **M01 — Live world/surface composition refresh**
2. **M02 — One-command rocky planet creation**
3. **M03 — Studio production-terrain runtime bridge**

This batch creates the minimum coherent runtime foundation required before attempting terrain rendering in Studio.

## Why M04 is not first

The current Studio Perspective viewport only has `BodyPreviewRenderer` for normal body presentation. Directly inserting a terrain renderer before M01–M03 would create fragile ownership:

- authoring edits would not have a guaranteed composition refresh boundary;
- terrain runtime resources would not have a generation-safe session owner;
- project/world/body switches could leave renderer-held references stale.

Therefore M04 consumes the stable bridge built by M03.

## Current known editor gaps

- `StudioRuntimeBinding::Refresh()` advances `StudioSession::Tick()`, but the Studio tick does not yet make the semantic-edit → `EditorWorldSession::RefreshUniverseIfChanged()` synchronization an explicit first step.
- `SurfaceAuthoringUi` already edits relief, biome preferences, local masks, material/scatter/process multipliers, but ordinary edits do not yet provide a full live terrain-regeneration feedback/status loop.
- normal Perspective presentation still uses `BodyPreviewRenderer`; it is not the V0.0.4 production terrain.
- Debug presentation and physical-page selection exist, but production terrain runtime pages must be published continuously into `TerrainDebugLivePages`.
- local biome override placement still exposes numeric unit-direction entry; viewport picking/painting must become the normal workflow.
- M04 authored terrain constraints are not yet a first-class Studio viewport tool.
- per-body `TerrainBodyServices` now exists, but process configuration is not yet fully semantic/editor-authored.

## Next implementation target

**Wait for V0.0.4 hardware/integration closure, then implement M01–M03 as one batch.**
