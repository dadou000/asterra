# Orbit V0.0.6 — Celestial Systems & Orbital Rendering Scaffold

Status: **Planned — scaffold frozen, implementation not started**

V0.0.6 turns Orbit's existing world/system/body foundation into a research-backed celestial authoring and rendering stack capable of building complex multi-body systems without sacrificing the simplicity of the Studio workflow.

The release is deliberately broad in capability but strict in architecture. Orbit must be able to author a simple moon in seconds and a deeply customized binary-star system, ring system, atmosphere, cloud stack, gas giant, airless moon, comet or other unusual body without requiring a second editor or a parallel data model.

The core design rule is:

> **Presets accelerate common cases. Capabilities, physical models and schema-driven authoring remain fully accessible underneath.**

The second design rule is:

> **Research establishes the default physical model; Orbit may intentionally diverge for gameplay or art, but every divergence must be explicit, localized and inspectable rather than hidden inside magic constants.**

The third design rule is:

> **A body has one semantic authority but may have many simulation and rendering representations. Ground clipmaps, orbital globes, far impostors and point proxies are derived representations of the same body.**

V0.0.6 builds directly on the accepted V0.0.5 Studio terrain workflow and the V0.0.3 universe/frame architecture. It must not replace the existing terrain authority or create a second celestial hierarchy.

---

# 1. Release outcome

From a clean Orbit Studio project, a user must be able to:

1. create a celestial system, including nested barycentric hierarchies;
2. create stars, rocky planets, moons, gas/ice giants, asteroids and other bodies from recipes or from empty capability composition;
3. author orbit, rotation, shape, mass, gravity, surface, atmosphere, clouds, oceans, rings, radiation and other implemented capabilities through the normal Inspector and contextual tools;
4. decide whether important properties are explicit, derived, procedural, imported or linked;
5. inspect how a derived value was obtained and which inputs constrain it;
6. visualize and edit orbits directly in a System View viewport with time control;
7. fly continuously from production terrain through atmosphere to orbit;
8. see the same terrain/climate/material authority represented by a macro-displaced orbital globe;
9. transition at far distance through smooth globe, analytic disc impostor and point/stellar proxy representations without visible identity changes;
10. obtain physically coherent stellar illumination, eclipses, planet/moon shine, atmospheric scattering and exposure;
11. author multilayer atmospheres, clouds and rings with deep exact controls rather than fixed template-only choices;
12. create complex procedural systems from deterministic seeds while retaining full control of generated results;
13. save/reopen the project and reconstruct the same semantic system while all derived GPU/render caches regenerate;
14. inspect representation LOD, celestial lighting, orbit state, solver provenance and derived cache status in Studio;
15. drive the same operations through UI, commands, plugins and MCP/agent tooling.

The primary acceptance scene is the Asterra system:

- Helion;
- Asterra;
- Luma;
- Umbra.

The release must also include stress scenes for:

- a binary or hierarchical multiple-star system;
- a ringed giant;
- an airless heavily cratered body;
- a thick-atmosphere world;
- a small far-away body that traverses the full globe -> impostor -> point ladder.

# 2. Permanent architecture rules

## 2.1 Existing FrameGraph remains the spatial backbone

Do not create a second celestial transform hierarchy.

System inertial frames, body frames, rotating frames, barycentric frames, local physics frames and surface frames remain explicit FrameGraph nodes.

A barycenter/reference node is not faked as a renderable planet.

## 2.2 Capability composition, not body-class inheritance

Do not build a hierarchy such as Planet -> RockyPlanet -> TerraPlanet or Star -> NeutronStar.

Body classifications are recipes, generation hints and editor presentation metadata only.

Runtime behavior comes from attached capabilities such as:

- reference shape;
- mass/gravity;
- rotation;
- orbit/ephemeris;
- surface;
- atmosphere;
- ocean;
- clouds;
- rings;
- radiative emitter;
- photosphere;
- corona;
- magnetosphere/aurora;
- comet tail;
- compact-object optics;
- accretion flow.

Plugins may register additional capability schemas through the same extension boundary.

## 2.3 One body authority, many representations

Persistent authority lives in semantic world records and referenced source assets.

Derived runtime representations may include:

- local production toroidal terrain clipmaps;
- regional/global terrain fields;
- macro-displaced orbital globe;
- smooth analytic globe;
- analytic disc impostor;
- cached impostor;
- point proxy;
- stellar point/disc proxy;
- atmosphere/cloud/ring LUTs and GPU volumes.

None of those derived forms become semantic authority.

## 2.4 Simulation LOD and rendering LOD are independent

A body may be dynamically simulated while rendered as one pixel.

A body may use an analytic Kepler orbit while its surface is rendered at full local terrain detail.

Do not couple physical fidelity decisions to visual representation decisions.

## 2.5 Physical units are explicit

Authoritative physical quantities use explicit SI units internally.

The UI may display astronomical units, Earth masses, solar radii, hours, days, degrees or other convenient units, but unit conversion occurs at the UI/schema boundary.

No unlabeled raw numeric field is accepted for a physical quantity.

## 2.6 Research-backed default, explicit custom override

Each major physical/render model must have:

- a research note in docs/research;
- stated assumptions and validity range;
- a deterministic reference test;
- a performance strategy;
- an explicit list of intentional simplifications.

Artistic/gameplay overrides are allowed, but must live in named override parameters or presentation layers rather than silently changing physical authority.

## 2.7 No arbitrary authoring caps

Do not impose fixed limits such as "maximum 4 moons", "maximum 10 cloud layers" or "one ring system" merely for UI convenience.

If a real runtime resource limit exists, expose it as a diagnosed implementation limit and design the semantic model so the limit can evolve.

## 2.8 Derived values retain provenance

Every solver-managed property must expose its source:

- Explicit;
- Derived;
- Procedural;
- Imported;
- Linked;
- Default.

The user can see what produced a value and, where mathematically valid, choose which variables are authoritative and which are solved.

## 2.9 Strong defaults do not lock the user

Recipes such as Rocky Planet, Airless Moon, Gas Giant or G-type Star create sensible capability sets and values.

They are not special runtime types.

After creation, every capability remains editable and removable when the resulting state is valid.

## 2.10 Unified Studio only

All celestial authoring lives inside the existing Orbit Studio executable and workspace.

There is no separate celestial editor, system builder, launcher or planet editor application.

## 2.11 Shared mutation path

Studio UI, contextual toolbar, orbit gizmos, plugins and MCP invoke the same validated commands and transactions.

No panel directly writes celestial SQLite records.

## 2.12 Customization is schema-first

Ordinary property authoring is generated from SchemaRegistry metadata.

A subsystem may provide a specialized visual editor, but exact properties remain discoverable through the Inspector and automation APIs.

# 3. Semantic celestial model

V0.0.6 extends the existing World -> Celestial System -> Celestial Body hierarchy with explicit non-renderable orbital/reference nodes and capability records.

Suggested semantic hierarchy:

~~~
World
  Celestial System
    Reference/Barycenter Node
      Star
      Star
      Planet
        Moon
        Ring System capability
        Atmosphere capability
        Cloud Layer records
~~~

A body record remains identity + relationship data. Capabilities own specialized configuration.

## 3.1 Core body properties

The body core owns only broadly shared physical identity:

- stable BodyId;
- owning SystemId;
- display/classification metadata;
- reference frame;
- parent/orbit reference;
- shape capability reference;
- optional mass-property capability;
- enabled capability records.

Do not dump atmosphere, ring, terrain and star fields into one universal body struct.

## 3.2 Property source/provenance model

Solver-managed properties use a common semantic wrapper conceptually equivalent to:

~~~
PropertyValue
  value
  sourceMode
  sourceObject/sourceAsset optional
  lockState
  solverStatus
  uncertainty optional
~~~

The stored schema may specialize by value type, but the Inspector must present a consistent model.

Supported source modes in V0.0.6:

- Explicit — authored exact value;
- Derived — solved from other constrained properties;
- Procedural — generated deterministically from a seed/recipe;
- Imported — source ephemeris/catalog/asset;
- Linked — follows another authored property or curve;
- Default — capability default not yet overridden.

## 3.3 Body recipes

Initial built-in recipes:

- Empty Celestial Body;
- Rocky Planet;
- Airless Moon;
- Ocean World;
- Thick-Atmosphere World;
- Asteroid/Irregular Small Body;
- Gas Giant;
- Ice Giant;
- Main-Sequence Star;
- White Dwarf;
- Neutron Star;
- Black Hole;
- Comet.

A recipe is a command that composes ordinary capabilities in one undoable transaction.

A recipe never creates a hidden runtime type.

# 4. Dynamics and astronomical state

## 4.1 Orbit state interface

All orbit models implement one runtime query contract:

~~~
EvaluateState(body, time, referenceFrame)
    -> position
       velocity
       orientation reference if required
       quality/provenance
~~~

Initial implementations:

- Fixed/attached state;
- analytic Kepler/conic orbit;
- imported sampled ephemeris;
- dynamic N-body state.

Later integrators can extend the same seam.

## 4.2 Barycenters and nested systems

The semantic/runtime model must support:

- planet -> moon;
- binary planet;
- binary star;
- hierarchical triple systems;
- circumbinary planets;
- nested local barycenters;
- free/rogue bodies.

A barycenter is an explicit reference/orbit node with no renderable surface requirement.

## 4.3 Analytic Kepler/conic model

Support elliptic, parabolic and hyperbolic trajectories where meaningful.

Authorable elements include at least:

- epoch;
- semi-major axis or periapsis form;
- eccentricity;
- inclination;
- longitude of ascending node;
- argument of periapsis;
- mean anomaly / equivalent phase;
- gravitational parameter source.

The solver must be unit-tested against analytic/reference cases.

## 4.4 Imported ephemeris adapter

Provide an adapter boundary capable of consuming sampled or SPICE-like ephemeris data without making a third-party library the engine API.

Imported data is a source asset; Orbit owns the runtime state-query interface.

## 4.5 N-body promotion

N-body is a selectable dynamics capability, not a requirement for all bodies.

The system must support promotion from analytic orbits to dynamic integration for bodies that need perturbations.

Integrator choice/settings are advanced controls and must report energy/angular-momentum drift diagnostics.

## 4.6 Rotation/orientation

Rotation is separate from orbital translation.

Initial support:

- fixed orientation;
- uniform spin;
- axial tilt;
- phase/epoch;
- synchronous/tidal lock mode;
- precession/nutation extension points.

# 5. Physical property solver

Orbit must support incomplete and over-constrained authoring without hiding what happened.

Examples:

- mass + radius -> density;
- radius + density -> mass;
- semi-major axis + parent gravitational parameter -> period;
- luminosity + effective temperature -> stellar radius where the selected model permits;
- atmospheric composition -> mean molar mass and scattering inputs;
- rotation period + radius -> equatorial velocity.

The solver has explicit constraints.

## 5.1 Constraint UI

Inspector rows display:

- value;
- unit;
- source badge;
- lock/solve state;
- validation status.

The user can choose which variables are locked.

Conflicting constraints produce a visible conflict with named properties; Orbit does not silently pick one.

## 5.2 Uncertainty

The semantic model should allow optional uncertainty/range metadata for imported astronomical data.

This is not required for ordinary fictional-world authoring but prevents the core schema from assuming every value is exact.

# 6. Gravity

Gravity remains a capability separate from shape and orbit.

V0.0.6 target models:

- point-mass / spherical;
- oblate J2 minimum;
- extensible zonal harmonic model;
- local surface gravity query;
- multi-body acceleration for promoted dynamic systems.

A surface gameplay query may use an optimized local model while the orbital dynamics system uses a higher-level source; both must be derived from named gravity authority rather than unrelated constants.

---

# 7. Celestial rendering representation ladder

The representation resolver chooses by projected error/apparent angular size, performance budget and feature requirements rather than altitude alone.

Required ladder:

~~~
production surface / toroidal clipmaps
        ↓ overlap
macro-displaced orbital globe
        ↓
smooth globe
        ↓
analytic or cached disc impostor
        ↓
point / stellar proxy
~~~

Representations overlap during transition.

## 7.1 Macro globe

Uses the same global terrain authority as production terrain but retains only orbital-scale detail:

- global elevation;
- giant basins/craters;
- continental mountain ranges;
- broad geology/material response;
- ocean/ice masks;
- global normals/roughness.

Macro displacement affects silhouette and terminator.

## 7.2 Smooth globe

Uses analytic sphere/ellipsoid geometry plus global appearance fields when geometric displacement is sub-pixel.

## 7.3 Analytic disc impostor

A camera-facing primitive reconstructs the projected sphere/ellipsoid analytically in shader space.

It may still evaluate:

- correct phase;
- terminator;
- limb response;
- global surface texture;
- simple atmosphere;
- eclipse mask;
- emission.

It is not a static JPEG billboard.

## 7.4 Cached complex impostor

Bodies with rings/cloud complexity may render a temporary view-dependent impostor cache.

Cache updates are driven by measurable appearance change, not every frame.

## 7.5 Point and stellar proxies

Sub-pixel bodies become point representations with radiometrically plausible brightness handling.

Multiple-star systems may use aggregate far proxies where appropriate while retaining their individual runtime bodies.

# 8. Planetary Appearance System

Introduce a derived appearance layer between physical world data and celestial rendering.

Inputs may include:

- global elevation;
- geology;
- sediment/weathering;
- biome/vegetation;
- snow/ice;
- ocean coverage;
- temperature/moisture;
- authored material overrides;
- city/night emission;
- cloud/weather state.

Derived products may include:

- global albedo;
- global normal field;
- macro elevation;
- roughness;
- ocean/ice masks;
- thermal/emission fields;
- representation-specific compressed textures.

These products are DDC/runtime caches, never world authority.

The existing production terrain source remains authoritative for terrain.

# 9. Celestial lighting and exposure

## 9.1 Radiometric emitter model

Stars and other emitters provide physical or physically-inspired radiance/irradiance data.

The renderer should not rely on arbitrary RGB directional lights for astronomical illumination.

## 9.2 Eclipse/occlusion service

Eclipse geometry is a shared celestial lighting service.

Support:

- partial;
- total;
- annular;
- multiple simultaneous occluders;
- ring attenuation extension;
- atmospheric twilight response.

A body does not need a scripted "eclipse event" for ordinary geometric eclipses.

## 9.3 Reflected illumination

Provide planet/moon shine through a bounded approximation suitable for real-time rendering.

The approximation and energy limitations must be documented.

## 9.4 Astronomical HDR/exposure

Scene-referred HDR must accommodate:

- stellar discs;
- sunlit clouds/surfaces;
- twilight;
- night side;
- city emission;
- stars.

Exposure/adaptation is a render-view concern and must not rewrite physical radiance authority.

---

# 10. Atmospheres

Atmosphere is a capability with physical and presentation data separated.

Authorable physical inputs include:

- reference bottom/top radius;
- pressure/density;
- gas composition;
- temperature/density profile;
- aerosols;
- ozone/absorbers where applicable;
- scale heights or profile curves;
- cloud coupling parameters.

Derived optical inputs include:

- Rayleigh coefficients;
- Mie/aerosol coefficients;
- absorption;
- phase parameters;
- spectral/RGB approximation data.

GPU LUTs are derived caches.

The first production model should follow a documented precomputed multiple-scattering approach suitable for arbitrary planet radius/profile, not Earth-only constants.

Advanced artistic controls may alter presentation gain/tint only through explicitly labeled override fields.

---

# 11. Clouds

Clouds are records/capabilities, not one texture slot.

Support an arbitrary semantic list of cloud layers/volumes.

Each layer may choose a source model:

- climate/weather driven;
- procedural;
- authored mask/texture;
- imported;
- disabled.

Authoring dimensions include:

- altitude range;
- coverage;
- density;
- optical properties;
- wind/advection;
- precipitation/phase metadata;
- detail/noise policy;
- shadow participation;
- orbital representation policy.

Ground and orbital representations must share recognizable weather authority even when they use different derived GPU data.

---

# 12. Oceans and fluid optical appearance

The existing terrain/water authority remains the source for surface coverage.

The celestial renderer adds an orbital ocean representation with:

- Fresnel response;
- roughness/wave statistics;
- stellar glitter;
- atmospheric attenuation;
- depth/coastal colour inputs where available;
- cloud reflection/occlusion approximation.

This is rendering derivation, not a second ocean simulation.

---

# 13. Ring systems

A ring system is a capability containing an arbitrary list of bands/components.

Authorable fields include:

- inner/outer radius;
- thickness;
- optical depth;
- particle-size distribution;
- albedo/phase response;
- density structure;
- warp/inclination;
- shadow participation;
- procedural structure seed;
- optional authored radial profile.

Rendering must distinguish front/back scattering through a physically motivated phase/optical model rather than a hardcoded two-colour texture where feasible.

LOD supports full ring geometry/volume close up and analytic/cached representation far away.

---

# 14. Stellar bodies

Stars use the same body/capability framework.

Initial capabilities:

- radiative emitter;
- photosphere;
- limb darkening;
- surface/granulation appearance;
- starspots/activity parameters;
- corona;
- flare extension point.

Stellar physical property derivation should expose source/provenance exactly like planets.

Far representation and close photosphere representation are separate render LODs.

---

# 15. Gas and ice giants

Gas/ice giants are not rocky planets with terrain disabled.

They use volume/atmospheric appearance capabilities and may expose:

- zonal bands;
- jet structure;
- storms/cyclones;
- cloud decks;
- compositional colour response;
- oblateness;
- depth/volume fields.

The generic field system remains the preferred home for dense scalar/vector fields.

---

# 16. Small bodies, comets and irregular shapes

The shape capability must retain the V0.0.3 requirement for irregular closed surfaces.

V0.0.6 adds authoring/render support for:

- irregular asteroids;
- large impact/crater hierarchy;
- low-gravity bodies;
- comet coma/tail capability;
- rotation/tumbling extension point.

Terrain clipmaps are not forced onto bodies where an irregular mesh/field representation is more appropriate.

---

# 17. Magnetosphere and aurora

Magnetosphere/aurora are optional capabilities.

The minimum V0.0.6 implementation may use a research-backed parameterized field/auroral-oval approximation, but the semantic API must be compatible with a future simulated magnetic/plasma field.

Aurora requires atmospheric context but does not become part of the atmosphere class.

---

# 18. Compact objects and accretion

The core capability model must be able to host:

- compact-object gravity/optics;
- accretion disk;
- jets;
- extreme emitter models.

V0.0.6 may stage the most expensive relativistic rendering behind later milestones, but no architecture may assume all bodies have a visible solid surface.

Any implemented lensing model requires a dedicated research/validation note.

---

# 19. Procedural system generation

Generation is deterministic and recipe-driven.

A generator may create:

- system hierarchy;
- barycenters;
- stars;
- planets;
- moons;
- asteroid populations;
- capability sets;
- initial physical properties;
- orbital architecture.

Generation output becomes ordinary semantic objects/capabilities.

The user may edit, remove or replace generated values.

The generator records:

- seed;
- recipe/version;
- generated-property provenance.

Regeneration must never silently overwrite explicit user edits.

# 20. Studio UI integration

## 20.1 Explorer

Explorer shows semantic hierarchy:

- systems;
- barycenter/reference nodes;
- bodies;
- capability children where useful;
- cloud/ring layer records.

Generated runtime render/cache nodes are diagnostic virtual children only.

## 20.2 Contextual creation

Selection drives shared commands:

- World -> Add Celestial System;
- System/Reference Node -> Add Body / Add Barycenter;
- Body -> Add Capability / Add Child Body;
- multiple bodies -> orbit/reference operations where valid.

"Add Capability" is searchable and categorized.

## 20.3 Inspector

The generic Inspector is the authoritative exact editing surface.

Property groups include:

- Identity;
- Physical;
- Dynamics;
- Rotation;
- Rendering/Appearance;
- capability-specific sections;
- Advanced;
- Diagnostics where read-only.

Solver-managed properties show source/provenance and lock state inline.

## 20.4 System View

Add a normal Studio viewport mode, not a separate window/application.

Features:

- system hierarchy visualization;
- orbit curves;
- barycenters;
- body labels;
- scale-aware body proxies;
- selection;
- focus;
- time scrub;
- play/pause/time scale;
- reference-frame choice;
- orbit handles/gizmos;
- projected habitable/thermal overlays only when implemented from real models.

## 20.5 Direct orbit editing

Where mathematically valid:

- drag periapsis/apoapsis;
- rotate orbital plane;
- adjust phase;
- numeric exact edit in Inspector;
- snap/copy/paste;
- undo/redo.

Gizmos commit through CommandService.

## 20.6 Preset/recipe UI

Recipes are exposed through a fast searchable creation surface.

The creation UI may show a few common high-level choices, but an Empty body path and full post-creation editing must always remain available.

## 20.7 Advanced customization

Advanced sections expose exact model parameters rather than hiding them permanently.

Search must find advanced properties even when collapsed.

Plugins and MCP receive the same schemas and commands.

## 20.8 Representation/debug UI

A selected body can show:

- current render representation;
- projected radius/error;
- transition weights;
- globe/impostor cache state;
- atmosphere LUT state;
- orbital appearance revision;
- lighting/eclipse contributors;
- physical-property solver status.

Debug state is read-only presentation.

# 21. CPU/GPU residency

| Data | Authority | Typical runtime residency |
| --- | --- | --- |
| body/system/capability records | SQLite semantic world | CPU |
| FrameGraph/orbit models | derived runtime | CPU double precision |
| N-body integration state | runtime simulation | CPU initially; GPU only if justified |
| global terrain/geology fields | existing terrain authority/derived fields | CPU descriptors + streamed GPU products |
| orbital appearance maps | derived DDC/runtime | GPU on demand |
| macro globe geometry | derived | GPU |
| atmosphere LUTs | derived | GPU |
| cloud volumes | derived | GPU, sparse/streamed as required |
| ring profiles | semantic + derived | CPU semantic, GPU render products |
| impostor cache | derived transient | GPU |
| point proxies | derived | compact GPU scene data |
| UI/schema/provenance | semantic/runtime metadata | CPU |

Do not mirror large fields to CPU and GPU without a consumer requirement.

# 22. Research and validation contract

Every milestone introducing a nontrivial physical/render model must link a research note that contains:

1. target phenomenon;
2. reference sources;
3. equations/model;
4. assumptions;
5. validity range;
6. numerical validation;
7. visual reference/benchmark where relevant;
8. GPU/CPU residency choice;
9. performance budget;
10. known intentional deviations.

SpaceEngine is a visual/feature reference, not a source-code or algorithm authority.

Scientific/technical sources take precedence for physical implementation.

V0.0.6 does not require:

Those systems may build on the V0.0.6 capability seams later.

# 27. Definition of "ridiculous customization"

For V0.0.6 this phrase has a concrete engineering meaning:

- capability lists are composable rather than hard-coded body classes;
- ordinary lists/layers are dynamically sized;
- values carry units and provenance;
- users can choose constraints/authoritative variables;
- presets are editable recipes;
- advanced model parameters are searchable;
- exact numerical editing exists beside visual tools;
- source assets and imported ephemerides are supported through adapters;
- presentation overrides are explicit;
- custom plugins can register schemas/commands/capabilities;
- MCP can inspect and drive the same model;
- derived/runtime state remains inspectable;
- unusual physically valid combinations are not rejected merely because they are uncommon.

The UI still presents a concise default path through progressive disclosure.

That balance — extremely deep capability under a simple contextual surface — is the V0.0.6 product target.
