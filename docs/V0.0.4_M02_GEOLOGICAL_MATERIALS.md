# Orbit V0.0.4 — M02 Geological Material Library

Status: **implemented**

Branch: `orbit`

Completed: 2026-09-17

M02 establishes the permanent authored material layer consumed by later geology and terrain-process milestones. Geological materials are substrate physics, not biome definitions and not renderer/PBR materials.

## 1. Authoritative record

`Orbit::TerrainGeology` owns the CPU-authoritative record:

```cpp
struct GeologicalMaterial
{
    RockTypeId id;
    std::string name;

    float hardness;
    float cohesion;
    float hydraulicErodibility;
    float aeolianErodibility;
    float permeability;
    float chemicalWeatherability;
    float fractureTendency;
    float density;
};
```

`RockTypeId` is a 128-bit `StrongId`. It is authored/persisted identity and is never derived from a GPU table index, clipmap location, camera state or terrain page.

The seven non-density physical coefficients are normalized authoring values in `[0, 1]`. `density` is bulk density in kg/m^3 and must be finite and positive.

The reference values in this milestone are physically ordered defaults intended to establish differential behaviour. They are not presented as a universal laboratory calibration; a project can author calibrated records without changing the runtime contract.

## 2. Initial reference materials

The five initial rock definitions are real `.orbitgeologicalmaterial` authority files under `engine/terrain_geology/assets/reference/`. Their physical coefficient values are data, not C++ defaults and not shader constants.

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Basalt | 0.92 | 0.90 | 0.10 | 0.05 | 0.08 | 0.35 | 0.55 | 2950 |
| Granite | 0.88 | 0.86 | 0.12 | 0.04 | 0.03 | 0.28 | 0.45 | 2700 |
| Sandstone | 0.55 | 0.50 | 0.58 | 0.45 | 0.65 | 0.38 | 0.60 | 2350 |
| Limestone | 0.52 | 0.62 | 0.42 | 0.25 | 0.35 | 0.90 | 0.65 | 2600 |

The stable IDs live under `terrain_geology::reference_rock` so code/tests can refer to identity without duplicating physical values. Their numeric values are persistence identity and must not be repurposed.

## 3. CPU authority and mutation

`GeologicalMaterialLibrary` stores authored records on the CPU and exposes:

- stable-ID lookup;
- case-insensitive name lookup for editor/search use;
- validated `Upsert` and `Erase` operations;
- a monotonic `Revision()`;
- immutable material enumeration;
- construction of the derived compact GPU table.

Invalid IDs, empty names, coefficients outside `[0, 1]`, non-finite values and non-positive density are rejected before they enter library authority.

A material edit increments the library revision. Consumers can map that revision into the V0.0.4 geology revision domain and invalidate derived pages/tables without making those derived representations authoritative.

## 4. Compact GPU representation

Shaders do not receive strings or 128-bit rock IDs for every material sample. The library builds a derived table of:

```cpp
struct alignas(16) GpuGeologicalMaterial
{
    float hardness;
    float cohesion;
    float hydraulicErodibility;
    float aeolianErodibility;

    float permeability;
    float chemicalWeatherability;
    float fractureTendency;
    float density;
};
```

The layout is exactly 32 bytes: two `float4` lanes. CPU-side `RockTypeId -> table index` mapping preserves authored identity while GPU terrain fields can store a compact integer material index.

The GPU table is derived state. Rebuilding or reallocating it does not alter the authored rock identity.

## 5. Authored file format and loading

`ParseGeologicalMaterialToml` and `SerializeGeologicalMaterialToml` define the project-authority representation for `.orbitgeologicalmaterial` assets:

```toml
[geological_material]
id = "4f524249-5452-4f43-4b00-000000000003"
name = "Sandstone"
hardness = 0.55
cohesion = 0.50
hydraulic_erodibility = 0.58
aeolian_erodibility = 0.45
permeability = 0.65
chemical_weatherability = 0.38
fracture_tendency = 0.60
density = 2350.0
```

`LoadGeologicalMaterialFile` loads one authority file. `LoadGeologicalMaterialDirectory` recursively discovers `.orbitgeologicalmaterial` files, sorts them by path for deterministic loading, validates each record and rejects duplicate stable IDs or case-insensitive names.

The codec validates the record on load and before serialization. The physical semantics remain owned by `TerrainGeology`; renderer material assets remain a separate system.

## 6. Differential erosion contract

M02 does not yet implement the full hydraulic/aeolian solvers. It establishes the intrinsic material response those later operators consume.

`EvaluateIntrinsicErosionResponse` applies identical external forcing to the authored intrinsic coefficients:

```text
hydraulic response = hydraulic forcing × hydraulicErodibility
aeolian response   = aeolian forcing × aeolianErodibility
chemical response  = chemical forcing × chemicalWeatherability
fracture response  = fracture forcing × fractureTendency
```

Climate, biome protection and authored process overrides are deliberately absent here. They are later multipliers/resolvers and must not overwrite the intrinsic rock record.

Under identical forcing, the M02 acceptance tests require basalt, sandstone and unconsolidated volcanic ash to produce measurably different hydraulic and aeolian response. Limestone additionally validates a distinct chemical-weathering response.

## 7. Acceptance coverage

`Orbit.TerrainGeologyMaterials` verifies:

- all five initial real material types are loaded from `.orbitgeologicalmaterial` authority files;
- the authored records match the frozen stable `RockTypeId` identities;
- every material has a unique stable ID;
- all authored coefficients pass the physical range contract;
- stable-ID and editor-oriented name lookup;
- identical forcing produces different responses for at least three rock types;
- CPU values survive compact GPU packing;
- individual-file loading and directory loading agree;
- TOML authority records round-trip;
- material edits preserve identity, increment revision and replace in place;
- invalid authored coefficients are rejected.

## 8. M02 invariants

1. **Rock identity is stable authored identity, never a GPU array index.**
2. **Intrinsic erodibility belongs to geology, not to a biome.**
3. **Renderer/PBR materials and geological physical materials remain separate.**
4. **CPU records are authority; the GPU material table is derived.**
5. **Terrain processes read material coefficients instead of hard-coded shader constants.**
6. **Reference physical coefficients live in authored files, not in C++ defaults.**
7. **Material definition does not contain stratigraphic geometry.**

## 9. Boundary of this milestone

M02 defines *what a rock material is*. It does not define where that material occurs vertically or spatially.

The next mandatory milestone is **M03 — Virtual Stratigraphy**: profiles, layer thickness/depth evaluation, folds/tilt/warp and exposed-layer lookup without a planet-wide voxel volume.
