# Orbit V0.0.4 — M11 Local GPU Hydraulic Erosion

Status: **implemented and verified**

Branch: `orbit`

Verified implementation head: `7d933037177f80a84a1c75680f590f65815bf72e`

Implemented: 2026-09-18

M11 adds the local hydraulic process layer on top of the large-scale M10
stream-power landform. It is a shallow-water/material-column solver, not a
droplet erosion system.

## 1. Solver state

Each physical cell carries the hydraulic state required by the frozen M11
contract:

```text
water depth
four virtual-pipe outflow fluxes
horizontal water velocity
suspended sediment
sediment carrying capacity
physical M08 material column
M08 moisture
```

CPU/reference suspended sediment is tracked as total kilograms per cell.
The GPU representation stores kilograms per square meter, which avoids
resolution-dependent numerical scale while retaining the same mass semantics.

## 2. Iteration order

One hydraulic step is:

```text
rain / water source
      ↓
virtual-pipe outflow
      ↓
water continuity + velocity
      ↓
sediment capacity
      ↓
M08 erosion / deposition
      ↓
conservative sediment advection
      ↓
infiltration → M08 moisture
      ↓
evaporation
```

The virtual-pipe update follows the Mei/Decaudin/Hu shallow-water model:
outflow increases from hydraulic-head difference, remains non-negative, and
all four outgoing pipes are scaled together when necessary so one step cannot
export more water volume than the cell contains.

## 3. Physical surface

Hydraulic head uses the current M08 top surface:

```text
bedrock
+ regolith
+ soil
+ sand
+ debris
+ water depth
```

M11 therefore erodes/deposits against the same mutable physical surface used by
M09/M10 rather than creating a separate erosion heightmap.

## 4. Sediment capacity

The local target concentration is velocity/slope driven:

```text
capacity concentration
    = capacityCoefficient
    × |velocity|
    × downhill slope
```

and is clamped to a configured maximum concentration.

The target mobile mass then follows from water volume/depth. A capacity deficit
causes erosion; a capacity excess causes deposition.

## 5. Layered erosion and geology resistance

CPU/reference erosion always calls M08 `MaterialColumnPage::Erode()`, so
removal order remains:

```text
debris → sand → soil → regolith → bedrock
```

The GPU kernel performs the same ordered layer removal directly on the M08
storage textures.

Loose-layer mobility is explicit per material class. When bedrock is exposed,
M02 controls resistance using:

- hydraulic erodibility;
- hardness;
- cohesion;
- density for mass conversion.

Hard competent rock therefore detaches much more slowly than soil/regolith or
soft rock under the same hydraulic forcing.

## 6. Deposition and transport

Eroded mass is added to suspended sediment rather than deleted.

Hydraulic deposition currently enters the M08 mobile sand lane. M14 later
generalizes this into shared typed sediment exchange between hydraulic,
aeolian and thermal processes.

Sediment advection uses the same four virtual-pipe water fluxes. For every
source cell, the transported fraction is bounded by the water volume actually
exported during that step, and that transported mass is distributed among the
receiving neighbors proportionally to directional flux.

M11 page boundaries are closed for mobile water/sediment. Cross-page mobile
sediment/water exchange is intentionally owned by M14's frozen unified
transport-boundary milestone rather than being duplicated here.

## 7. Infiltration and moisture

Infiltration depends on:

- configured infiltration rate;
- M02 bedrock permeability;
- remaining M08 moisture capacity.

Infiltrated water is removed from surface water and increases the existing M08
normalized moisture channel. Moisture is clamped to `[0,1]`.

Evaporation is applied afterward as a deterministic first-order water loss.

## 8. Material mass conservation

M11 exposes two independent mass-balance checks.

### Process ledger

```text
eroded mass
= deposited mass
+ final suspended mass
+ boundary loss
```

Closed M11 pages currently have zero boundary sediment loss.

### Physical M08 column check

For a process epoch with no tectonic displacement:

```text
initial loose mass
+ excavated bedrock mass
= final loose mass
+ suspended sediment mass
```

Acceptance requires the independent physical-column relative error to remain
below **2×10^-5**. This tolerance accounts for repeated f32 layer storage while
still detecting meaningful material creation/deletion.

## 9. GPU implementation

`GpuHydraulicErosionPage` owns persistent fixed-capacity buffers for:

```text
water                    N² × f32
flux                     N² × float4
velocity                 N² × float2
suspended sediment       N² × f32
local sediment scratch   N² × f32
material snapshot        N² × 6 × f32
```

No hydraulic-state heap/GPU-resource allocation occurs per step.

The solver uses seven HLSL compute stages:

1. initialize state;
2. rain + virtual-pipe flux;
3. continuity + velocity;
4. capacity erosion/deposition;
5. conservative sediment transport;
6. infiltration + evaporation;
7. physical material snapshot.

M08 textures are used directly:

```text
R32F      bedrock
RGBA16F   regolith / soil / sand / debris
RG16F     moisture / process
R16_UINT  M02 material-table index
```

The GPU M02 table uses the same stable order supplied to
`PackGpuPage()`.

## 10. CPU authority handoff

M08 remains CPU authority.

After GPU simulation, `RecordMaterialReadback()` writes a compact
24-byte-per-cell snapshot containing:

```text
bedrock
regolith
soil
sand
debris
moisture
```

The snapshot is copied through a normal buffer readback, avoiding any need to
extend Orbit's texture-readback path.

After the command-list fence completes,
`ApplyMaterialReadbackToCpu()` updates the CPU `MaterialColumnPage` while
preserving:

- reference bedrock elevation;
- stable RockTypeId;
- temporary/process identity.

The GPU simulation therefore does not become an independent terrain authority.

## 11. Determinism

The CPU reference path contains no stochastic ordering or droplet sampling.
Fixed physical state, rainfall field and configuration produce identical
hydraulic state and material columns.

GPU kernels use one deterministic cell update per pass and explicit ping-pong
buffers. The M11 shader set is compiled through Orbit's DXC Vulkan path in CI.

## 13. Reference direction

The hydraulic flow organization follows the Mei, Decaudin & Hu virtual-pipe
GPU erosion family: shallow-water flow generates a velocity field, which drives
erosion/deposition and sediment transport.

The layered-material/moisture direction also matches the architecture used by
Oasis 2025, while Orbit keeps its own M02 geological physics and M08
CPU-authoritative material-column contract.
