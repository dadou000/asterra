# Orbit V0.0.3 — Celestial Authoring Scaffold

Status: **active implementation — M22 implementation in-tree; acceptance and M23 integration proof in progress**

Branch target: `orbit`

This document defines the V0.0.3 scaffold for Orbit. It is intentionally broader than a
terrain milestone. V0.0.3 turns the current planet/terrain prototype into the permanent
foundation of a game engine whose primary authoring problem is building complex,
procedural, moving celestial environments through a simple contextual editor.

The design target is not only Earth-like terrain. Orbit must be able to grow cleanly from
rocky planets and moons to irregular asteroids, gas giants, stellar objects, pulsars and
compact objects without replacing the world model each time.

The V0.0.3 implementation must be production-shaped. **Do not add placeholder classes,
temporary editor APIs, throwaway serializers, fake body types, or systems that are known
to be replaced later.** If a capability is not implemented yet, it does not exist yet.
Every type introduced in this milestone must have a real owner, real persistence rules,
real runtime semantics, tests, and a stable public boundary.

---

## 1. V0.0.3 goals

V0.0.3 establishes the following permanent engine pillars:

1. A frame-aware celestial world model that supports many moving bodies.
2. A time model suitable for rotation, orbital motion and simulation scheduling.
3. Composition-based celestial body capabilities instead of a planet inheritance tree.
4. A generic field and procedural dependency system that is not terrain-specific.
5. A persistent project/document model with save/load and schema migration.
6. A command/transaction model shared by the editor, gameplay tools, plugins and MCP.
7. A Roblox-Studio-inspired editor shell with docking, contextual toolbars, tree inspector,
   property inspector, radial actions, drag/drop assets and resizable viewports.
8. A first-class external plugin system.
9. Extensive MCP control generated from the same schema/command registries used by the
   editor.
10. A material/asset service for rapid drag/drop assignment of textures, decals, PBR
    materials and reusable content.
11. A first-class procedural path/network system for roads, rail, waterways, AI reference
    rails and space routes, including anchors on moving bodies and moving entities.
12. Headless project building and cooking that uses the same pipeline as the editor.
13. A platform-services boundary with a real Steam backend for achievements, stats and
    game-recording timeline events.
14. A clean route from the existing `OrbitSandbox` terrain stack into the new scaffold
    without discarding working terrain code.

V0.0.3 is not the milestone where every celestial phenomenon is implemented. It is the
milestone where the architecture stops assuming that every world is one spherical rocky
planet.

## 2. Permanent technology decisions

These choices are part of the scaffold and should not be treated as temporary UI or
tooling experiments.

| Layer | Choice | Reason |
| --- | --- | --- |
| Engine/runtime/editor host | **C++23** | Existing Orbit codebase, explicit memory/control, Vulkan integration, deterministic engine boundaries. |
| GPU programs | **HLSL compiled with DXC to SPIR-V** | Already established in Orbit; keeps shader authoring unified while Vulkan remains the active RHI backend. |
| Editor UI implementation | **Dear ImGui docking + Orbit-owned UI abstraction** | Excellent docking, high-frequency tooling UI, native integration with the renderer, easy multi-viewport composition. Plugins never depend directly on ImGui. |
| Game/editor scripting | **Luau** | Fast embeddable VM, sandboxable, hot-reloadable, friendly for external plugin authors, and intentionally familiar to Roblox Studio users. |
| External editor plugins | **Luau packages** | Avoids forcing plugin authors onto Orbit's C++ ABI while still allowing rich tools, panels, commands and importers. |
| MCP adapter | **Python 3.12+** | Protocol/tooling boundary only. Python does not enter the engine process. The existing MCP bridge evolves into the permanent adapter around a structured engine RPC API. |
| Project manifest | **TOML** | Human-readable, stable, simple for source control and build profiles. |
| Authoritative world documents | **SQLite databases with explicit schema versions and migrations** | Transactions, indexed hierarchy queries, large sparse semantic worlds, partial loading, robust crash recovery. Generated geometry is never stored as authority. |
| Derived asset cache | **Content-addressed Derived Data Cache (DDC)** | Imported/compiled data is reproducible from source + importer version + settings and is therefore disposable. |
| Engine/editor RPC | **JSON-RPC 2.0 over loopback WebSocket or local IPC transport** | Typed structured calls, request/response IDs, notifications, easy MCP mapping and future remote editor tooling. The protocol contract is independent of transport. |

### 2.1 Why Dear ImGui rather than a web UI

Orbit's primary editor contains live Vulkan viewports, high-frequency selection tools,
profilers, gizmos, material previews and procedural graph inspectors. Keeping the editor
inside the same native rendering/runtime process avoids browser embedding, texture
handoff and input synchronization layers.

Dear ImGui is not exposed as the plugin contract. Orbit owns an `EditorUi` API and
command registration system. This keeps the UI implementation replaceable in principle
without making the plugin ecosystem depend on implementation details, while Dear ImGui
itself is intended as the long-term V0.0.3 editor implementation.

### 2.2 Why Luau for plugins

Luau is the default language for:

- editor plugins;
- project automation scripts;
- lightweight gameplay scripting;
- custom contextual tools;
- custom importers that do not require native decoding libraries;
- command callbacks;
- validation rules.

Engine-critical systems, RHI backends, heavy simulation and native import codecs remain
C++23.

V0.0.3 does **not** implement arbitrary native third-party DLL plugins. Native engine
extensions require a separately versioned ABI and are outside this milestone. Luau is a
complete plugin solution, not a temporary stand-in.

## 5. CPU/GPU residency rules

Orbit must distinguish **authority** from **residency**. GPU data is generally derived
runtime state, not project authority.

| Data/system | Authoritative location | Runtime residency | Reason |
| --- | --- | --- | --- |
| Project manifest | Disk/TOML | CPU | Small configuration and build metadata. |
| World object hierarchy | SQLite | CPU, lazily loaded | Needed for editing, commands, save/load and deterministic semantic state. |
| Object IDs / schemas / property metadata | CPU | CPU | Used by editor, serialization, plugins and MCP. |
| Frame graph | CPU double precision | CPU; compact camera-relative transforms copied to GPU | Hierarchical motion and numerical precision require CPU authority. |
| Simulation time | CPU integer epoch time | CPU; frame constants copied to GPU | One authoritative clock, many derived GPU consumers. |
| Celestial body definitions | SQLite/CPU | CPU | Semantic configuration, not render data. |
| Procedural dependency graph | CPU | CPU | Scheduling/invalidation problem; graph is sparse. |
| Dense scalar/vector fields | Descriptor/revision on CPU | GPU pages when computation/rendering benefits; CPU pages only when gameplay queries need them | Dense field math is highly parallel; do not mirror all data by default. |
| Terrain clipmaps | CPU control state | GPU-heavy sample/render buffers with selective CPU caches | Existing Orbit direction; keep CPU authority and GPU derived residency. |
| Render graph | CPU compiled schedule | GPU resources/passes | CPU decides dependencies; GPU executes. |
| GPU scene | Derived from active scene | GPU | Rendering-only representation. |
| Tree inspector model | CPU | CPU | Metadata/UI state only. |
| Editor widget geometry | CPU generated | GPU rendered | Standard immediate-mode editor path. |
| Material definitions | Disk/CPU | CPU metadata + GPU descriptors/resources when visible | Avoid loading all textures into VRAM. |
| Source textures/assets | Disk | CPU staging only during import as needed | Source is not runtime residency. |
| Cooked texture/mesh data | DDC/disk | GPU streamed on demand | Platform-optimized derived form. |
| Path network graph | SQLite/CPU | CPU | Sparse semantic topology, selection, routing and AI access. |
| Path visual mesh | Derived cache | GPU | Disposable visualization/road surface geometry. |
| Path collision/nav samples | Derived cache | CPU/physics backend | Consumers need queryable geometry. |
| Sparse graph routing | CPU jobs | CPU | Low-frequency graph problem with branching. |
| Dense route cost fields | CPU descriptors | GPU when large | Terrain/slope/depth costs can be evaluated in parallel. |
| MCP state | Out-of-process Python + engine RPC | CPU | Never enters render/simulation hot paths. |
| Steam/platform state | CPU | CPU | SDK callbacks, stats and achievements are control-plane work. |

### 5.1 Residency rule

A system must not copy data to both CPU and GPU simply because both exist. Each consumer
must state why it needs residency. Readback is asynchronous and explicit.

### 5.2 Generated geometry rule

Terrain mesh, road mesh, collision, navigation, material thumbnails, HLOD and preview
images are derived caches. Their authoritative source is semantic project data.

## 6. Universe, frames and time

### 6.1 IDs

Introduce stable IDs:

```cpp
using ProjectId = StrongId<...>;
using WorldId   = StrongId<...>;
using SystemId  = StrongId<...>;
using BodyId    = StrongId<...>;
using FrameId   = StrongId<...>;
using ObjectId  = StrongId<...>;
using AssetId   = StrongId<...>;
using FieldId   = StrongId<...>;
using NetworkId = StrongId<...>;
```

User-authored persistent objects use 128-bit IDs. IDs survive save/load, reparenting and
renaming.

### 6.2 Frame graph

A position is never just an unqualified global `Double3`.

Permanent position types distinguish:

- frame-relative transform;
- surface coordinate;
- entity/socket anchor;
- render-relative float transform.

Example:

```cpp
struct FramePoint
{
    FrameId frame;
    math::Double3 localMeters;
};
```

The frame graph stores parent-child transforms as functions of simulation time.

Typical hierarchy:

```text
System inertial frame
  Helion frame
    Asterra orbital frame
      Asterra rotating body frame
        regional frame
          local physics frame
            vehicle frame
              ferry-deck road-node frame
```

The frame graph is the answer to the apparent problem that "every path node moves because
the planet moves." A road node is stationary in the rotating body frame. A ferry deck node
is stationary in the ferry frame. Orbit resolves both to a common frame only when needed.

### 6.3 Time

Introduce:

```cpp
struct SimulationTime
{
    i64 microsecondsFromEpoch;
};
```

Microseconds give long astronomical range while local physics continues to consume
double-precision delta seconds.

The time service owns:

- project epoch;
- simulation time;
- real-time scale;
- pause/step;
- fixed simulation clocks;
- interpolation time for rendering.

Systems declare their own update cadence; there is no requirement that climate, orbit,
physics and rendering tick at one rate.

## 7. Celestial body composition

Replace the assumption that a planet is defined by one radius with a body registry and
capability composition.

A body always has:

- `BodyId`;
- name;
- owning `SystemId`;
- body frame;
- mass properties if physically relevant;
- enabled capabilities.

Capabilities are data + services, not subclasses.

Examples:

```text
Rocky planet
  Shape
  Gravity
  Rotation
  Surface
  Atmosphere
  Hydrosphere
  FieldSet

Asteroid
  IrregularShape
  Gravity
  Rotation
  Surface
  FieldSet

Gas giant
  ReferenceShape
  Gravity
  Rotation
  VolumeFieldSet
  Atmosphere
  Cloud layers
```

Future stellar/compact-object capabilities register through the same body/capability
registry. V0.0.3 must not add empty `Pulsar` or `BlackHole` classes merely to claim
support.

### 7.1 Body shape contract

The permanent shape API must support at least:

- analytic sphere/ellipsoid reference surfaces;
- height-displaced reference surfaces;
- irregular closed surfaces.

A surface-capable body can expose coordinate conversion and local tangent frames without
forcing every body in the universe to have terrain.

### 7.2 Migration of current terrain

The existing Asterra terrain pipeline becomes an implementation of a surface capability.

Current terrain code should continue to own:

- terrain generation;
- hydrology;
- erosion;
- terrain fields;
- terrain cache;
- clipmaps;
- water integration.

The body capability supplies its reference shape/frame rather than using one implicit
global planet.

## 8. Generic field system

The existing terrain fields should evolve into a general field service.

Supported semantic field kinds:

```text
ScalarField
VectorField
CategoricalField
MaterialField
TensorField
```

Supported domains are registered rather than hard-coded into field type:

```text
surface domain
volume domain
atmospheric shell
local region
body interior
free-space region
```

A field descriptor contains:

- `FieldId`;
- owning object/body;
- domain;
- value format;
- units;
- source evaluator;
- dependency revision;
- resolution policy;
- residency policy.

A field implementation may be CPU, GPU or hybrid. The API does not promise a CPU mirror.

Examples:

```text
rocky world: elevation, rock, rainfall, groundwater
gas giant: pressure, density, velocity, cloud density
pulsar future capability: magnetic field, plasma density, radiation
accretion flow future capability: density, velocity, temperature
```

## 9. Procedural dependency graph

V0.0.3 introduces a real dependency/invalidation graph instead of implicit generator
ordering.

Example:

```text
Orbit + rotation
      |
      v
 Insolation
      |
      v
 Temperature -----
      |            |
      v            v
 Atmospheric   Ice state
 circulation      |
      |            |
      v            |
 Precipitation ----
      |
      v
 Erosion
      |
      v
 Hydrology
      |
      v
 Biomes
```

Changing axial tilt should invalidate relevant climate descendants, not tectonics.

Each node declares:

- inputs;
- outputs;
- execution backend;
- deterministic input hash;
- invalidation rules;
- asynchronous build job;
- completion revision.

The graph owns scheduling; editor UI and MCP only request changes/builds.

## 10. Project and document format

### 10.1 Project layout

Permanent project folder layout:

```text
MyGame/
  Project.orbit.toml
  Content/
  Worlds/
    Main.orbitworld
  Scripts/
  Plugins/
  Config/
  Build/
  .orbit/
    DerivedData/
    Intermediate/
    Logs/
```

`.orbit/DerivedData` and `.orbit/Intermediate` are disposable and ignored by source
control.

### 10.2 Project manifest

`Project.orbit.toml` stores:

- project ID;
- project display name;
- engine compatibility version;
- startup world;
- enabled plugins/packages;
- script entry points;
- build profiles;
- platform integrations;
- asset mount points.

### 10.3 World database

Each `.orbitworld` is an SQLite database containing semantic records:

- object hierarchy;
- body records;
- capability records;
- generator configuration;
- path networks;
- user-authored entities;
- material assignments;
- project-specific deltas;
- command journal checkpoints where required.

The DB schema has an explicit integer schema version and ordered migrations.

Do not store generated terrain mesh, road mesh, GPU buffers, texture thumbnails or
render targets in the world database.

### 10.4 Saves versus projects

The editor project is authoring state.

Runtime save games are separate sparse state documents derived from the project's world
schema. A game build never modifies its source `.orbitworld`.

## 12. Command, transaction and selection model

### 12.1 One mutation path

All authoring changes go through validated commands:

```text

MCP client
Gameplay construction tool
      |
      v
 Command Registry
      |
      v
 Validation
      |
      v
 Transaction
      |
      v

```

No editor widget writes directly into world records.

### 12.2 Transactions

Commands are grouped into transactions with:

- begin;
- apply;
- commit;
- rollback;
- undo;
- redo.

A drag gizmo may apply many preview updates but commits one semantic transaction.

### 12.3 Selection service

A central `SelectionService` owns ordered multi-selection of `ObjectId` values.

The tree, viewport, property inspector, radial menu, plugins and MCP all observe the same
selection state.

### 13.1 Contextual toolbar system

Toolbars are generated from command metadata.

A command can declare:

- required selected type/capability;
- allowed selection count;
- editor mode;
- category;
- icon;
- shortcut;
- radial menu group;
- toolbar group;
- enable predicate.

Selecting two path nodes automatically exposes connection tools. Selecting a celestial
body exposes body/world tools. Selecting a material exposes material operations.

Plugins register commands through the same registry.

### 13.2 Radial actions

Radial menus are command views, not separate logic.

For two selected path nodes the default radial actions include:

- Connect Direct;
- Connect Bézier;
- Connect Routed;
- Reverse/Swap connection intent where meaningful;
- Create network from selection if nodes are not yet owned by one.

The radial UI invokes ordinary commands, so MCP and plugins can invoke the same operation.

### 13.3 Gizmos

Transform/selection gizmos are editor tools layered over the command model.

Gizmos operate in an explicit frame:

- world/inertial;
- body;
- parent;
- local;
- surface tangent.

This is required for moving planets and moving parent entities.

It represents the semantic object hierarchy, not the GPU scene.

Required behavior:

- stable `ObjectId` identity;
- expand/collapse;
- multi-selection;
- type icons;
- rename;
- search/filter;

- folders;
- lock;
- editor visibility;
- context menu;
- plugin-provided tree actions;
- reveal current selection;
- copy object path/ID;

Generated procedural output is not expanded into millions of persistent tree objects.
The tree shows the generator/network/body that owns it.

## 15. Resizable and multiple viewports

Every editor viewport is a `RenderView`, not a special singleton window.

A view owns:

- camera state;
- view frame;
- target body/scene;
- render mode;
- debug overlays;
- exposure;
- selection/picking buffers;
- offscreen color/depth targets.

ImGui displays the offscreen target in a dock panel. Resizing reallocates the target
through the render graph.

Users can split or duplicate viewports. Different viewports may show:

- perspective;
- top/orthographic;
- body map;
- material preview;
- alternate debug field;
- another body/frame.

The swapchain belongs to the editor window; individual viewports render offscreen.

## 16. Render graph and GPU scene

Before editor systems multiply direct RHI usage, add a render graph above the existing
Vulkan RHI.

The render graph owns:

- pass dependencies;
- transient resources;
- image/buffer state transitions;
- per-view targets;
- lifetime aliasing where safe;
- timestamp ranges;
- queue assignment where supported.

The existing terrain renderer is migrated as a render-graph client without changing its
authoritative terrain model.

A separate `GpuScene` contains render-only instances extracted from active simulation or
editor preview state.

Persistent world objects never contain Vulkan handles.

## 17. Asset database and Material Service

### 17.1 Asset registry

Every imported asset receives an `AssetId`.

The authoritative registry tracks:

- source path;
- source hash;
- asset type;
- importer ID/version;
- import settings;
- dependencies;
- cooked outputs;
- tags;
- thumbnail key.

The registry is CPU-side. Cooked data is stored in the DDC.

### 17.2 Supported V0.0.3 asset categories

- Texture2D;
- PBR material;
- material instance;
- decal;
- mesh;
- reusable object/prefab;
- Luau script;
- path profile;
- plugin package metadata.

### 17.3 Material Service panel

The panel behaves as a fast asset browser:

- folders/collections;
- search;
- tags;
- thumbnails;
- favorites/recent;
- import;
- drag/drop;
- PBR material assembly;
- decal preview;
- material instance creation.

Dropping an asset onto a compatible scene object resolves the drop intent and issues a
command such as:

```text
AssignMaterial
AttachDecal
SetTextureProperty
InstantiatePrefab
```

The UI never mutates a renderer object directly.

### 17.4 PBR material definition

The baseline material schema supports:

- base color;
- normal;
- roughness;
- metallic;
- ambient occlusion;
- emissive;
- opacity/mask where supported;
- UV transform;
- scalar/vector overrides.

Imported map sets can be auto-detected by filename conventions, but the importer UI must
allow explicit map assignment before commit.

### 17.5 GPU material residency

Source images stay on disk.

The import pipeline creates platform-ready compressed texture products in the DDC.
Visible/needed products stream to GPU memory. Material metadata remains CPU resident.

The material system should evolve toward descriptor indexing/bindless resource access in
the Vulkan backend rather than allocating a bespoke descriptor layout for every material.

## 20. Procedural path/network system

The path system is a core Orbit system, not a road-specific editor tool.

It must represent:

- roads;
- railways;
- footpaths;
- waterways;
- shipping lanes;
- aircraft routes;
- AI reference rails;
- vehicle-deck continuation paths;
- space navigation/reference routes.

### 20.1 Core data model

```text
PathNetwork
  NetworkId
  profile AssetId
  Nodes[]
  Edges[]

PathNode
  ObjectId
  Anchor
  tags
  constraints
  connection metadata

PathEdge
  ObjectId
  start node
  end node
  connection mode
  geometry parameters
  profile override
```

### 20.2 Anchor model

A node does not own one absolute world position.

Supported anchors:

```text

  BodyId
  stable surface coordinate

  ObjectId / runtime entity ID

  local transform
```

This makes all ordinary planet infrastructure naturally dynamic in inertial space while
remaining static relative to its body.

A road painted onto Asterra is body-local.

A road reference on a ferry deck is ferry-local.

A rail connector on a moving vehicle can be socket-local.

### 20.3 Edge modes

V0.0.3 implements three real connection modes:

#### Direct

Straight connection in the edge's evaluation frame/domain.

#### Bézier

Cubic Bézier connection with authorable handles and curvature inspection.

#### Routed

The system computes the path between the two anchors using a selected `PathProfile`
and cost sources.

This is the "dynamic connection" authoring mode.

A routed edge stores semantic routing intent plus the resolved route revision. The route
is recomputed asynchronously when one of its relevant dependencies changes.

### 20.4 Path profile assets

A `PathProfile` defines constraints/costs instead of hard-coding "road" into the graph.

Examples:

#### Road profile

- minimum radius;
- maximum grade;
- lane/width rules;
- terrain cut/fill costs;
- bridge/tunnel permissions;
- water crossing cost;
- preferred corridor fields.

#### Rail profile

- much tighter grade limit;
- curve radius;
- turnout rules;
- bridge/tunnel costs.

#### Water profile

- minimum depth;
- land exclusion;
- current/wind cost inputs;
- clearance.

#### Space reference profile

- obstacle/exclusion zones;
- body/frame anchors;
- time-dependent endpoint evaluation.

V0.0.3 space paths are geometric/reference routes. Orbital transfer optimization is a
future path solver capability and must not be faked in this milestone.

### 20.5 Dynamic endpoints across frames

If both nodes share one parent frame, the edge geometry remains local and moves with that
frame at effectively zero recompute cost.

If endpoints belong to different frames, the edge evaluates both anchors at
`SimulationTime`.

Depending on edge mode:

- Direct: endpoint transforms update continuously; no expensive route solve is required.
- Bézier: control handles are stored in a declared frame and transformed consistently.
- Routed: solver invalidation is based on relative-frame motion thresholds and dependency
  revisions, then solved asynchronously.

This distinction prevents "the planet moves, so every road has to be recalculated."

### 20.6 Routing residency

The semantic network and sparse topology stay on CPU.

Dense cost surfaces such as slope, depth or terrain buildability may be produced on GPU.

The route solver runs as CPU jobs over sparse graph/tile structures and queries cached
cost data. This is a branching search problem and is not moved to GPU merely for novelty.

### 20.7 Derived products

From the semantic network Orbit may derive:

- visible road/rail/waterway mesh;
- lane centerlines;
- AI navigation graph;
- collision surface;
- signs/markers;
- procedural sleepers/ties;
- bridge/tunnel requests;
- terrain modification requests.

All are caches. The network remains authority.

### 20.8 Editor workflow

Default workflow:

1. Activate Path tool.
2. Place node A.
3. Place node B.
4. Multi-select both nodes.
5. Contextual toolbar and radial menu expose:
   - Connect Direct;
   - Connect Bézier;
   - Connect Routed.
6. The new edge appears immediately in the tree/network inspector.
7. Properties expose profile, width, grade, handles or routing constraints.
8. Changing terrain/profile invalidates only routed edges that depend on the changed
   inputs.

## 26. Architectural invariants added by V0.0.3

1. **No unqualified persistent world positions.** Persistent spatial data is anchored to
   a frame, surface or entity/socket.
2. **No renderer authority.** GPU data is always derived from semantic state.
3. **No editor-only mutation path.** Editor, plugins and MCP use commands.
4. **No terrain assumption in the universe layer.** Surface is optional.
5. **No generated geometry as source of truth.**
6. **No plugin dependency on ImGui internals.**
7. **No Steamworks calls in game/domain code.**
8. **No cache required to reopen a project.**
9. **No global service locator.**
10. **No empty capability types merged for future marketing claims.**
11. **Every system states CPU/GPU residency and ownership.**
12. **Every persistent schema has a version and migration strategy.**
13. **Every asynchronous generator result is revision-checked before commit.**
14. **All body/path transforms resolve through the frame graph at an explicit simulation
    time.**
15. **MCP tools are generated from engine capabilities where possible rather than becoming
    a second manually maintained editor API.**

This is the scaffold V0.0.3 should protect as Orbit expands.
