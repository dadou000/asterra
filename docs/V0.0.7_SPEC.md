# Orbit V0.0.7 — Dynamic Lighting, GI & HDR Presentation Scaffold

Status: **Scaffold frozen — implementation starts at M01**

V0.0.7 turns Orbit's current radiometric/HDR foundation into one production lighting pipeline that works continuously from ground scale to orbital scale, with or without hardware ray tracing.

The release is not a "ray tracing mode". It is a unified lighting system whose visibility work can be answered by screen traces, analytic/procedural scene representations, software tracing or Vulkan hardware ray queries according to cost and quality.

The core design rule is:

> **Hardware RT accelerates selected visibility queries. It does not select a different lighting model and it does not automatically increase the lighting budget.**

The second design rule is:

> **Emission is radiance. Any emissive material may contribute to GI, from a single LED pixel to a city visible from orbit, while representation detail collapses automatically with distance.**

The third design rule is:

> **Lighting is independent from geometric representation. Production terrain, macro globe, far globe/impostor and local scene geometry feed the same lighting semantics even when their render representations differ.**

The fourth design rule is:

> **Physical radiance is never rewritten to satisfy the display. Exposure, eye response, bloom/glare, tone mapping, LUT correction and SDR/HDR output are presentation stages downstream of lighting and GI.**

V0.0.7 builds on V0.0.6 M14-M19: celestial representation selection, macro/far rendering, Planetary Appearance, radiometry and the scene/display boundary. The remaining V0.0.6 celestial milestones remain valid and may feed V0.0.7 later; atmospheres, clouds, rings and specialized bodies are not allowed to create parallel lighting systems.

---

# 1. Release outcome

From one Orbit Studio project, the user must be able to:

1. light the same scene with one lighting model whether hardware RT is unsupported, disabled, available or enabled;
2. move continuously from metre-scale ground scenes to orbital views without switching to a different lighting engine;
3. use physically meaningful emissive materials that illuminate nearby surfaces through GI;
4. render an LED/video screen whose local colors contribute spatially to nearby indirect light instead of collapsing immediately to one average light;
5. aggregate the same emissive authority to regional/city/planetary representations at long distance;
6. receive dynamic diffuse GI from sun, sky, local lights and emissive materials with no baked-light requirement;
7. receive reflections through one quality hierarchy using screen data, cache data and optional exact visibility;
8. preserve stable performance budgets when hardware RT is enabled;
9. meter scene luminance with a GPU histogram instead of a raw arithmetic average;
10. retain the useful cone/rod asymmetry from the Godot Asterra eye-adaptation system;
11. stop normal exposure from chasing arbitrarily bright clouds, solar reflections or other extreme highlights;
12. represent excess brightness as saturation/headroom compression, bloom and glare, with fast photopic recovery;
13. support slower dark adaptation independently from transient bright overload;
14. keep GI/emissive energy unchanged by exposure, tone mapping, LUT correction or output display capability;
15. use a centralized HDR presentation chain with no renderer-local tone mapping;
16. apply color-correction LUTs through a documented scene/display color-management contract;
17. support SDR and HDR output policies without changing physical lighting;
18. expose simple default controls and complete advanced controls through the unified Orbit Studio UI;
19. inspect which visibility backend, cache level, emitter representation and performance budget produced the current lighting result;
20. validate visual continuity and performance on hardware with and without ray-query support.

Primary validation scenes:

- **LED Room** — a high-resolution animated RGB screen lights walls/floor with spatially varying emissive GI;
- **Cloud Glare** — sunlit bright clouds exceed comfortable/display headroom without driving exposure downward without bound;
- **Dark Interior -> Daylight** — validates light adaptation, dark adaptation and recovery;
- **Headlight / Brake Light** — small bright dynamic emitters remain stable and do not require explicit proxy lights;
- **City Night Flight** — local lamps aggregate into regional emission while descending/ascending;
- **Ground -> Orbit** — no lighting identity pop across terrain/globe/far representations;
- **RT A/B** — hardware RT off/on preserves the lighting model and approximate frame budget while improving visibility quality.

# 2. Permanent architecture rules

## 2.1 One lighting model

Diffuse GI, emissive GI, sky lighting, reflection integration and direct-light energy semantics are shared across all hardware tiers.

Prohibited:

- separate "RTX GI" and "non-RTX GI" implementations;
- RT-only emissive lighting;
- enabling hardware RT automatically multiplying rays-per-pixel or bounce count;
- content requiring artists to author duplicate lights for RT and non-RT modes.

Allowed:

- different visibility backends;
- different cache refresh density;
- different exact-hit rate;
- quality settings that explicitly request a larger budget.

## 2.2 Capability is not budget

GPU capability answers whether a backend exists.

A render budget answers how much work may be spent.

Keep separate runtime state conceptually equivalent to:

~~~cpp
struct GpuLightingCapabilities
{
    bool accelerationStructures;
    bool rayQuery;
    bool rayTracingPipeline;
    bool subgroupOperations;
};

struct LightingBudget
{
    float directLightingMs;
    float giMs;
    float reflectionMs;
    float emissiveMs;
    float postProcessMs;
};
~~~

The Balanced/Auto policy must not increase the total budget simply because ray-query hardware is detected.

## 2.3 Cheapest sufficient visibility

Lighting callers request visibility/transport intent, not a named hardware backend.

The scheduler may answer with:

1. screen-space trace;
2. analytic/procedural intersection;
3. terrain/heightfield hierarchy;
4. coarse proxy/software scene traversal;
5. Vulkan ray query.

Triangle BVH traversal is a fallback tool, not the universal world representation.

## 2.4 Specialized geometry stays specialized on RT hardware

Even when ray queries are available:

- planet intersection may remain analytic;
- production terrain may use hierarchical heightfield visibility;
- virtual/implicit heightfields may use cell traversal;
- water may use analytic/simplified optical surfaces where valid;
- vegetation may use RT proxies;
- ordinary meshes/vehicles/buildings may use acceleration structures.

Hardware RT must not force terrain into enormous triangle BLAS structures when the heightfield hierarchy answers the query more cheaply.

## 2.5 Emission is radiance

A material emission channel is part of physical lighting authority.

It is not synonymous with bloom and is not merely a visual additive term.

Material emission may expose:

- emission texture/color;
- physical luminance or radiance scale;
- GI contribution multiplier;
- reflection contribution;
- optional explicit artistic override.

Bloom/glare consume exposed camera radiance later and cannot feed GI.

## 2.6 One emissive authority, many LODs

A local screen, lamp, sign, road network or city may have many derived emitter representations:

- texel/pixel-level emissive surface;
- emissive tile hierarchy;
- local sampled emitter cluster;
- regional emission field;
- planetary emission field.

All are derived from the same authored/material authority.

A city visible from orbit must not be painted into unrelated albedo simply to appear luminous.

## 2.7 Lighting coordinates are body/frame stable

GI cache identity must not use camera-relative floating-origin coordinates as authority.

Persistent/retained lighting cache keys use stable world/body/frame addressing. GPU positions may be camera-relative.

Body-relative cache addressing must survive ordinary floating-origin rebases and representation transitions.

## 2.8 Representation replacement must not replace lighting semantics

Production terrain, macro globe, smooth globe, analytic disc and point representations are allowed to carry different lighting detail, but must preserve common quantities where meaningful:

- direct stellar illumination;
- broad sky/atmospheric irradiance;
- emission;
- reflected/indirect aggregate energy;
- eclipse/occlusion state.

Transitioning representation may change frequency/detail, not the identity of the light source or material.

## 2.9 Scene-linear HDR is authoritative for presentation

No local terrain/globe/far renderer performs final display tone mapping.

The presentation chain owns exposure and output conversion.

Intermediate lighting values may exceed 1.0 by arbitrary physically required amounts.

## 2.10 Exposure is not highlight destruction

Normal photopic adaptation has a calibrated upper target/ceiling.

Scene values above that ceiling remain in HDR and feed:

- highlight compression;
- bloom;
- glare/flare;
- optional overload/bleaching response.

They do not force the adaptation target toward infinity.

## 2.11 Dark adaptation and bright overload are separate state

Eye response has at least three independent concepts:

- photopic exposure/adaptation;
- dark adaptation / cone-to-rod sensitivity;
- transient bright overload.

A short bright-cloud glance must be able to recover quickly even though deep dark adaptation remains slow.

## 2.12 LUT/color correction never changes physical lighting

Color correction is presentation/color management.

A display LUT may modify displayed color after tone mapping.

A future scene-referred grading LUT must use an explicit shaper/log encoding and still remain downstream of GI.

## 2.13 Progressive disclosure in Studio

Default Lighting settings remain short and usable.

Advanced settings expose exact cache levels, budgets, trace distances, history thresholds, emitter detail, exposure statistics, response constants, tone-map/output parameters and debug views.

Do not remove advanced capability to make the common panel simple.

## 2.14 Unified application only

No separate lighting editor, launcher, HDR calibration application or RT configuration executable.

Lighting authoring, graphics settings, diagnostics and profiling are Orbit Studio surfaces.

## 2.15 No placeholder implementation

A milestone may introduce a narrow production slice, but it may not land a fake renderer that is expected to be replaced wholesale later.

New APIs must be the intended long-term seam even if only one backend/algorithm is implemented initially.

# 4. Shared surface contract

V0.0.7 introduces a common lighting-facing surface contract.

Logical fields include:

~~~cpp
struct SurfaceData
{
    float3 worldPosition;
    float3 geometricNormal;
    float3 shadingNormal;

    float3 baseColor;
    float roughness;
    float metallic;

    float3 emissionRadiance;
    uint materialId;
    uint surfaceClass;

~~~

The exact GPU packing is implementation-specific and performance-driven.

Required adjacent data:

- reverse-Z depth;
- motion vectors;
- stable surface/instance identity sufficient for temporal rejection;
- optional material reconstruction key;
- representation provenance for diagnostics.

The first implementation may use a compact deferred surface buffer. V0.0.7 does not require a bindless visibility-buffer conversion before lighting can ship.

# 5. Direct lighting

## 5.1 Celestial light sources

V0.0.6 radiometry remains the source for stellar energy.

Direct stellar illumination uses:

- resolved radiative state;
- body/light geometry;
- atmosphere transmittance when available;
- eclipse/transit attenuation when V0.0.6 M20 exists;
- distance scaling from physical source state.

A hard-coded preview sun is not accepted in production surface/globe renderers.

## 5.2 Local lights

Local authored/runtime lights enter a clustered/tiled light-culling path.

Initial supported families should include at least:

- point;
- spot;
- area/rect extension seam;
- emissive surface sampling remains separate from explicit local-light records.

Local-light intensity uses explicit units where practical.

## 5.3 Shadow strategy

Direct shadowing is selected by source/scale:

- celestial/far occlusion: analytic/shared celestial service;
- sun/stellar terrain scale: shadow clipmap/cascade or equivalent large-scale solution;
- near contact: optional visibility queries;
- local lights: cached map, dynamic map or visibility query according to budget.

GI does not become responsible for resolving every primary shadow.

# 6. Unified visibility service

Introduce a lighting visibility contract conceptually equivalent to:

~~~cpp
enum class VisibilityPurpose
{
    DiffuseGi,
    Reflection,
    Shadow,
    SkyVisibility,
    ProbeUpdate
};

struct VisibilityQuery
{
    Ray ray;
    VisibilityPurpose purpose;
    float maxDistanceMeters;
    float requiredPrecision;
    float importance;
    uint allowedBackends;
};

struct VisibilityResult
{
    bool hit;
    float distanceMeters;
    float3 position;
    float3 geometricNormal;
    uint materialId;
    uint instanceId;
    uint backend;
    float confidence;
};
~~~

The caller does not request RTX, software BVH or terrain traversal directly.

Backends register capabilities and cost/quality estimates.

# 7. Non-RT visibility path

The non-RT path is a first-class supported configuration, not a compatibility afterthought.

Its hierarchy is:

1. screen trace when the required information exists;
2. analytic body/water/simple primitive intersection;
3. terrain/heightfield hierarchy;
4. simplified scene proxy/software traversal;
5. cache/environment fallback.

The release must be visually usable with no hardware ray query support.

Software traversal must use purpose-built coarse geometry/proxies and bounded budgets rather than trying to reproduce hardware BVH traversal at arbitrary detail.

---

# 8. Hardware ray-query path

Vulkan capability detection must distinguish:

- acceleration structures;
- ray query;
- full ray-tracing pipeline.

V0.0.7 lighting primarily needs **ray query** integration from ordinary compute/graphics shaders.

Hardware RT is used only when the scheduler decides it is the cheapest/most valuable backend for a query.

Default Balanced behavior:

~~~
same GI algorithm
same emissive system
same cache
same approximate frame budget

RT off -> more software/cache fallbacks
RT on  -> more exact off-screen hits inside the same budget
~~~

Cinematic/explicit quality modes may increase budgets, but that is a user policy choice rather than a capability side effect.

# 9. Lighting scheduler and budgets

Introduce a GPU-time-aware lighting scheduler.

Inputs:

- target frame time;
- user quality profile;
- measured pass timings;
- viewport resolution;
- scene motion/disocclusion;
- cache dirty state;
- emitter changes;
- backend capabilities.

Outputs may adjust:

- number of cache probes updated;
- exact visibility-query rate;
- screen-trace distance;
- reflection fallback density;
- emissive emitter sampling;
- spatial reuse radius;
- temporal reuse amount;
- far-field refresh rate.

The scheduler must degrade gracefully rather than toggling whole lighting identities.

# 10. Radiance cache

Diffuse GI is cache-driven on all hardware tiers.

Use camera-local **radiance clipmaps** whose identity is body/frame stable.

A conceptual ladder:

~~~
L0  room / vehicle scale
L1  building scale
L2  block scale
L3  district scale
L4  regional scale
far  planetary irradiance/emission field
~~~

Exact dimensions are quality/performance parameters, not frozen constants.

Each cell/probe tracks enough directional information for diffuse response and enough validity state for temporal updates.

Candidate representation:

- low-order SH for diffuse irradiance;
- distance/visibility moments;
- update age;
- confidence/variance;
- source revision/dirty state.

The implementation must document memory cost per level.

---

# 11. Cache residency and temporal stability

Radiance cache behavior must support:

- toroidal/clipmapped scrolling;
- stable body/frame addressing;
- incremental relocation;
- dirty-region invalidation;
- camera cut handling;
- disocclusion/history rejection;
- temporal confidence;
- update prioritization;
- separate static/stable vs dynamic emitter refresh pressure.

A camera movement alone must not invalidate physically unchanged world lighting more than required by residency.

---

# 12. Diffuse GI final gather

Visible surfaces receive indirect light from:

- short-range screen-space tracing for high-frequency local detail;
- radiance cache interpolation for stable lower-frequency energy;
- optional exact visibility fallback when screen/cache confidence is insufficient;
- far-field planetary/sky irradiance outside local GI range.

The initial production target is low stochastic ray/query density plus temporal/spatial reuse, not brute-force rays per pixel.

Multi-bounce behavior should primarily emerge through cache feedback rather than recursive per-pixel tracing.

---

# 13. Emissive material model

Material emission has explicit physical semantics.

A practical diffuse-emitter authoring model may expose:

- chromaticity/color or texture;
- luminance in cd/m^2 (nits) for surface emitters;
- optional radiance-power mode for specialized assets;
- GI contribution multiplier;
- reflection contribution;
- enable/disable participation.

For a Lambertian emitter, conversion between luminance/radiance quantities must be documented.

A texture can modulate local emitted radiance.

The visible material and the GI source use the same evaluated emission.

---

# 14. Emissive hierarchy and LED/video screens

Do not create one Light object per emissive texel.

Build a hierarchical emissive representation from the evaluated emission texture/surface:

~~~
full texel detail
   -> small tiles
      -> larger tiles
         -> surface regions
            -> whole emitter
~~~

The hierarchy stores energy/importance and color/spatial bounds.

Sampling probability is driven by emitted power/luminance and projected relevance.

Near a large LED wall, separate colored regions can illuminate different walls.

At distance, those regions collapse naturally into coarser emitters.

---

# 15. Small-emitter importance sampling

Tiny bright emitters are difficult for purely stochastic GI to discover.

V0.0.7 therefore supports explicit sampled-emitter promotion driven by measurable energy/projected size.

Large surfaces may be reached naturally by GI rays and sampled hierarchically.

Small high-energy regions receive direct importance samples and combine with the general GI estimator without double counting.

No artist-authored fake point light is required for ordinary emissive materials.

---

# 16. Dynamic emissive updates

Classify emitter change behavior:

- stable/static;
- slowly changing;
- rapidly changing/video;
- burst/transient.

Track emissive hierarchy tiles for meaningful radiance changes.

When an emitter changes:

1. mark affected hierarchy nodes dirty;
2. identify nearby radiance-cache regions;
3. prioritize those regions temporarily;
4. converge quickly;
5. decay update priority once stable.

A video screen must not invalidate the entire planet-scale GI cache every frame.

---

# 17. Planetary emission field

Introduce a derived planetary emission representation.

Inputs may include:

- authored/material emissive surfaces;
- city/road/airport/industrial aggregates;
- lava/fire/thermal-visible extensions;
- dynamic regional emitters.

Outputs may include:

- local detailed emitter hierarchy;
- regional emission tiles;
- global cube/spherical emission field;
- far-body emission summary.

Planetary Appearance may consume the far representation.

The field is derived cache data, not semantic authority.

---

# 18. Reflections

Reflections use the same visibility/cache architecture but a separate quality scheduler.

Suggested policy:

- very smooth: screen hit -> exact visibility fallback -> environment;
- medium roughness: reduced-rate exact visibility + temporal reuse;
- rough: radiance cache;
- fully rough: diffuse GI result.

Roughness must reduce expensive query demand rather than merely blurring an equally expensive perfect reflection.

---

# 19. Sky visibility and atmosphere coupling

Outdoor indirect lighting needs explicit sky visibility/occlusion.

The lighting system consumes sky radiance from the atmosphere/sky provider and estimates visible solid angle through cache/visibility sampling.

When V0.0.6 physical atmosphere LUTs exist, they feed sky radiance/transmittance.

Without them, a bounded fallback sky model may be used, but the contract remains the same.

Atmosphere does not own a separate GI system.

---

# 20. Orbit-to-ground continuity

Lighting frequency changes with geometric representation, but broad energy remains continuous.

Ground scale:

- screen final gather;
- dense local radiance cache;
- detailed emissive hierarchy;
- local reflections.

Aerial/regional:

- coarser cache levels;
- aggregated emissive tiles;
- atmosphere/sky coupling.

Orbital:

- planetary direct illumination;
- broad reflected irradiance;
- global/planetary emission field;
- atmosphere/cloud/ring consumers when available.

Representation overlap must preserve lighting state where practical rather than clearing all history at the handoff.

---

# 21. Luminance histogram

Replace simple arithmetic-average auto exposure with a GPU log-luminance histogram.

Track at minimum:

- robust central/median statistic;
- upper-middle percentile;
- high percentile;
- peak/near-peak energy.

Separate statistics serve separate purposes:

- normal exposure target;
- highlight/overload detection;
- bloom/glare extraction;
- diagnostics.

Allow exclusion/weighting of UI/debug overlays from exposure metering.

---

# 22. Human eye response

Carry forward the useful behavior of the Godot Asterra HumanEyeExposure implementation, but separate its coupled states.

Required state concept:

~~~cpp
struct EyeAdaptationState
{
    float photopicExposure;
    float darkSensitivity;
    float overload;
    float bleaching;
};
~~~

Bleaching may remain zero/disabled until sustained-extreme behavior is implemented, but its state seam must not be confused with ordinary overload.

Photopic adaptation:

- relatively fast;
- logarithmic;
- hysteresis around steady state;
- calibrated upper adaptation target.

Dark adaptation:

- cone phase;
- delayed/slower rod contribution;
- logarithmic sensitivity progression;
- reset/bleach behavior when returning to meaningful daylight.

Overload:

- very fast attack;
- fast release for ordinary bright-cloud/headlight glare;
- driven by excess scene luminance beyond the normal adaptation range;
- affects camera/display perception, not physical GI.

---

# 23. Bright-light ceiling and recovery

Define an adaptation-target ceiling in calibrated scene luminance/exposure space.

For metered luminance L:

~~~
normalAdaptationTarget = min(L, photopicCeiling)
excess = max(0, log2(L / photopicCeiling))
~~~

The exact ceiling is calibration data, not an arbitrary display-white constant.

Excess energy may drive:

- highlight compression;
- local saturation;
- bloom;
- veiling glare;
- flare;
- optional bleaching for sustained extreme exposure.

When the bright source leaves the view, transient overload can recover rapidly because normal exposure never chased the extreme value.

---

# 24. Bloom, glare and flare

Treat these as distinct effects.

Bloom:

- energy spread around bright image regions;
- soft-knee extraction;
- scale-dependent blur/pyramid;
- works in exposed HDR before final tone mapping.

Glare:

- broader contrast loss/veiling from extreme brightness;
- driven by excess energy and overload state.

Flare:

- optional optical artifact model for sufficiently intense compact sources;
- not triggered by every pixel slightly above display headroom.

Display peak luminance may influence presentation/headroom mapping, but scene energy is not clamped to the display peak.

---

# 25. Tone mapping and display headroom

Replace provisional/debug tone mapping with one centralized production presentation operator.

Requirements:

- preserve hue/chroma through highlights as far as practical;
- map scene-linear HDR into a display-referred working range;
- accept explicit exposure;
- expose reference white;
- expose target display peak luminance;
- keep operator choice/parameters inspectable.

No upstream renderer may duplicate this curve.

---

# 26. LUT correction and color management

The existing V0.0.7-start post-process LUT seam becomes the color-correction service.

Support:

- packed-2D 3D LUT GPU representation while RHI lacks native 3D textures;
- trilinear reconstruction;
- identity LUT;
- adjustable strength;
- .cube or equivalent LUT import;
- deterministic asset fingerprinting;
- display-referred LUT mode;
- scene-referred grading mode only through an explicit log/shaper transform.

Color spaces must be named at boundaries. Do not label arbitrary RGB values "linear" without defining the working primaries/transfer assumptions.

GI always consumes scene radiance before LUT correction.

---

# 27. SDR and HDR output

Output transforms are separate from tone mapping/LUT grading.

At minimum support:

- SDR output;
- HDR-capable path with explicit reference white and peak luminance policy;
- display-capability fallback when exact monitor metadata is unavailable.

A project's artistic grade must not depend on a single physical monitor peak.

The same physical scene should retain intent across output targets, accepting that highlights may be represented differently.

# 29. Quality policies

Quality settings are budget policies, not different rendering engines.

| Tier | Core behavior |
| --- | --- |
| Low | Direct + sky approximation + screen/local AO + sparse cache; no required RT |
| Medium | Screen GI + radiance cache + software/specialized visibility |
| High | Full cache + screen gather + optional ray-query fallback |
| Ultra | Higher exact-hit/cache refresh density within larger explicit budget |
| Cinematic | Explicitly larger GI/reflection/emissive budgets |
| Reference | Later progressive path-traced validation path; not required for V0.0.7 ship |

RT availability may improve a tier's result/cost, but does not redefine the tier.

# 31. CPU/GPU residency

## CPU

Persistent CPU authority:

- semantic lights/materials;
- material emission settings;
- graphics/project settings;
- stable body/frame identities.

Derived CPU data:

- visibility proxy metadata;

# 32A. Universal volumetric system

V0.0.7 includes a first-class universal field/volume framework inspired by the useful workflow properties of modern interactive fluid/VFX tools: a small simulation can drive richer 3D presentation, effects can follow terrain, many source types can feed one domain, and near-field interactive simulation can transition to cheap passive far-field representations.

The goal is not one solver pretending that smoke, water, fire, sand and snow are physically identical.

The goal is one **domain/source/field/render/cache/UI framework** into which specialized solver families plug.

## 32A.1 Supported effect families

The semantic framework must be able to represent at least:

- smoke;
- fog/mist;
- clouds;
- fire/combustion;
- dust/sand;
- snow/spindrift;
- steam;
- generic gas/plasma-like VFX;
- surface water flow/wakes/splashes;
- generic scalar/vector field effects.

Presets configure ordinary components. They are not hard-coded runtime subclasses.

## 32A.2 Domain modes

A volume domain selects a representation/solver policy rather than a different authoring model.

Required modes:

1. **Surface-aligned 2D/2.5D live domain**
   - follows terrain/mesh surfaces;
   - stores compact density/velocity/etc. fields;
   - can drive 3D volume rendering, surface response and particles;
   - preferred for large interactive ground effects.

2. **Local 3D live domain**
   - bounded 3D field around an effect/vehicle/structure;
   - sparse/tiled residency where practical;
   - intended for effects requiring true vertical structure.

3. **Layered/world volume**
   - large atmospheric/fog/cloud fields with coarse simulation or authored data;
   - integrates with planetary/body coordinates.

4. **Baked/cache playback**
   - derived field sequence, flowmap, flipbook or compact volume asset;
   - no live solver cost when interaction is unnecessary.

5. **Passive procedural representation**
   - far-field/detail representation driven by procedural patterns or coarse fields;
   - used when interactive simulation is not visually justified.

The scheduler may promote/demote between these representations according to distance, projected detail, interaction and budget.

## 32A.3 Common field channels

The framework supports typed field channels rather than a fixed monolithic voxel struct.

Initial channel vocabulary may include:

- density;
- velocity;
- temperature;
- pressure;
- fuel;
- oxidizer / combustion progress;
- humidity / condensate;
- signed distance / occupancy;
- surface height/depth;
- foam;
- sediment/particulate concentration;
- color/emission;
- user/plugin scalar/vector channels.

A solver declares which channels it reads/writes.

The renderer declares which channels it consumes.

## 32A.4 Inputs / sources / effectors

A domain may consume sources/effectors from:

- textures/bitmaps/masks;
- procedural fields;
- terrain/material masks;
- meshes and collision/SDF proxies;
- splines/paths;
- particles;
- destructible events;
- bones/skeletal attachment points;
- vehicle/world motion;
- weather/wind fields;
- authored viewport painting;
- other simulation domains through explicit coupling.

Source types include:

- density/mass injection;
- velocity/impulse;
- heat;
- fuel;
- moisture;
- obstacle/collision;
- sink/dissipation;
- attractor/vortex/wind;
- surface wetness/deposition.

## 32A.5 Outputs

The same field authority can drive:

- volumetric density rendering;
- emissive fire/plasma radiance;
- volume shadows/transmittance;
- GI scattering/emission;
- surface wetness/soot/snow/sand/deposition masks;
- flow/detail maps;
- GPU particles;
- wake/trail behavior;
- gameplay queries where explicitly requested;
- baked/cache assets.

A simulation is not forced to render as a volume. A surface-aligned water-flow domain may primarily drive surface shading and particles.

## 32A.6 Large-area strategy

Large worlds must not allocate a dense 3D grid around the whole planet.

Use a hierarchy such as:

- near interactive domain follows player/camera/important actor;
- medium range retains lower-frequency/coarser fields;
- far range uses passive procedural/baked patterns;
- planetary/weather authority provides broad boundary conditions.

Domain movement must preserve stable world/body coordinates and reuse valid field state where possible.

## 32A.7 Lighting integration

Volumes are first-class lighting participants.

The shared lighting pipeline must support:

- extinction/transmittance;
- single/multiple-scattering approximation;
- shadowing;
- direct stellar/local light injection;
- emissive volume radiance;
- GI contribution where budget allows;
- volume-to-surface and surface-to-volume lighting exchange;
- reflection/refraction hooks for appropriate media.

Fire is therefore not "orange fog + bloom". Its emissive field can inject radiance into the same GI system as emissive materials.

Cloud/fog lighting must use the same physical stellar/sky authority as surfaces.

## 32A.8 Performance and solver scheduling

Volume simulation and rendering have independent budgets.

The scheduler may vary:

- active domain resolution;
- number of solver iterations;
- update frequency;
- advection order;
- pressure solve budget;
- shadow sampling;
- raymarch step count;
- temporal reuse;
- near/far representation;
- particle coupling rate.

Hardware RT availability must not automatically increase volumetric simulation cost.

## 32A.9 Baked and imported data

Support a durable asset seam for:

- Orbit-native compact field caches;
- flipbooks;
- flowmaps;
- volume texture sequences;
- future VDB/OpenVDB-style import where useful.

Imported/baked data is source/derived asset data, not a different rendering architecture.

The design should favor compact representations when they reproduce the required effect instead of requiring large dense 3D caches.

## 32A.10 Volumetric authoring UI

Studio must expose a dedicated contextual **Volumes** toolset inside the unified application.

Default workflow:

1. Add Volume.
2. Choose preset: Smoke, Fog, Cloud, Fire, Dust/Sand, Snow, Water Flow, Empty.
3. Place/resize the domain in the viewport.
4. Add one or more sources.
5. Choose Live, Baked or Auto representation.
6. Press Play/Simulate or let Auto update.
7. Inspect the result directly in the production viewport.

Viewport interactions:

- domain box/surface gizmo;
- source position/radius/cone handles;
- spline source editing;
- terrain brush source painting;
- obstacle visualization;
- slice planes;
- velocity vectors;
- density/temperature/fire debug views;
- follow-player/follow-object volume visualization.

Inspector groups:

~~~text
Volume
├─ Preset / Solver
├─ Domain
├─ Sources
├─ Fields
├─ Advection / Dissipation
├─ Buoyancy / Wind / Forces
├─ Combustion / Phase (when applicable)
├─ Surface Coupling
├─ Rendering
├─ Lighting
├─ LOD / Residency
├─ Cache / Bake
└─ Advanced / Diagnostics
~~~

Presets hide irrelevant controls by default but never remove access to the underlying schema.

## 32A.11 UI/automation parity

Every volume creation/edit/simulation-cache operation available from Studio must route through shared model/service commands.

Plugins and MCP must be able to:

- create/remove domains;
- add/remove sources;
- change solver/settings;
- request bake/cache operations;
- inspect simulation state and performance;
- query derived asset status.

The viewport is a client of these services, not a separate authority.

# 35. Explicit non-goals

V0.0.7 does not require:

- a full recursive path-traced gameplay renderer;
- a vendor-specific NVIDIA-only lighting backend;
- replacing all terrain visibility with triangle acceleration structures;
- a baked lightmap workflow;
- a separate lighting or volumetric editor;
- replacing climate/weather/celestial atmosphere authority with the local VFX volume solver;
- one physically identical solver for every fluid/material phase;
- spectral rendering across the whole engine;
- physically exact eye biology;
- lens-manufacturer-specific flare simulation;
- mandatory native 3D LUT texture support before packed LUTs can ship.

A progressive path-traced reference renderer remains a later validation/quality target once the shared material/light/ray-scene contracts are mature.

# 36. Definition of success

The release succeeds when a user can place an animated emissive LED screen in a dark room, see its individual color regions illuminate nearby surfaces, fly outside and eventually see that same authored emission aggregate into the distant world, while Orbit automatically chooses suitable visibility/cache representations.

Turning hardware RT on must not transform the renderer into a heavier second mode. It should make difficult visibility queries cleaner/faster within the selected budget.

Looking at an extremely bright cloud or light source must not make exposure adapt downward forever. Normal adaptation reaches its calibrated photopic range, excess energy becomes glare/bloom/highlight compression, and transient overload recovers rapidly when the source leaves the view.

All of that must remain one lighting and presentation architecture from ground to orbit.

The same release must also let a user create and manipulate smoke, fog, fire, dust/sand, snow and surface-flow effects through one universal volume framework in Studio, choose live/baked/automatic representation, see those volumes react to the shared lighting/GI system, and scale from interactive near-field behavior to cheap far-field presentation without authoring a separate effect for every distance.
