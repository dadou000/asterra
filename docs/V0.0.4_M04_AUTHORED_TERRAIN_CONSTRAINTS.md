# Orbit V0.0.4 — M04 Unified Authored Terrain Constraints

Status: **implemented and verified**

Branch: `orbit`

Completed: 2026-09-17

M04 establishes the permanent project-authority representation for authored terrain intent. Constraints survive regeneration because the constraint records are persisted; generated terrain remains derived and disposable.

## 1. Authority boundary

```text
project authority
  TerrainConstraintSet
    ├─ height
    ├─ gradient
    ├─ uplift
    ├─ material
    ├─ protection
    └─ drainage
          ↓
canonical body-space evaluation
          ↓
procedural / terrain-process consumers
          ↓
derived terrain pages and caches
```

A generated canyon mesh/height page is never project authority. Rebuilding from the same `.orbitterrainconstraints` asset must reproduce the same constraint sample.

## 2. Unified field set

M04 implements the scaffold contract directly:

```cpp
struct TerrainConstraintSet
{
    HeightConstraintField height;
    GradientConstraintField gradient;
    UpliftConstraintField uplift;
    MaterialConstraintField material;
    ProtectionConstraintField protection;
    DrainageConstraintField drainage;
};
```

The set also owns stable `TerrainConstraintSetId`, `PlanetId`, and a display name. Every individual constraint owns a stable `TerrainConstraintId`. Duplicate IDs within a set are invalid.

## 3. Authoring primitives

All fields use the same canonical primitive representation:

- point;
- brush with inner plateau and outer falloff;
- spline with half-width and falloff;
- polygon with optional exterior falloff;
- raster mask with canonical tangent anchor, orientation, cell spacing and normalized samples.

Primitive geometry is stored in body-space unit directions or in a tangent raster anchored by a body-space unit direction. No primitive stores cube-face UVs, clipmap coordinates, viewport state or cache slots.

Spline distance is evaluated against spherical great-circle segments. Polygon and raster primitives use an M01 canonical tangent frame. This preserves constraint phase across cube-face seams.

## 4. Composition modes

M04 implements all scaffold modes:

```text
Add
Subtract
Replace
Multiply
Min
Max
```

For scalar and gradient fields, primitive influence and authored opacity continuously blend the selected operation.

Material constraints use the same modes against a bounded four-material derived blend. Material IDs remain M02 `RockTypeId` values; the constraint system does not create renderer materials or redefine rock physics.

## 5. Protection / preservation semantics

Protection is a process coefficient, not an immutable terrain lock.

```text
erosionAllowance = 1 - clamp(protection, 0, 1)
```

Therefore:

- protection `0` = normal terrain-process erosion;
- protection `0.6` = 40% of the unprotected erosion amount remains active;
- protection `1` = complete authored preservation when explicitly requested.

This allows an authored canyon to retain its intended form while weathering and erosion can still act inside and around it.

## 6. Canyon authoring

A canyon does not require a special canyon runtime object. One spline primitive can be referenced by independent field constraints:

```text
spline
  ├─ height      -150 m
  ├─ protection  replace 0.60
  ├─ drainage    +1.0
  └─ material    optional authored override
```

The height field establishes authored geometric intent. Drainage can guide later hydrology. Protection controls how later erosion modifies the result. Because all are independent fields, changing preservation does not destroy or rewrite the authored spline.

## 7. Imported raster masks

`RasterMaskConstraintPrimitive` stores a real sampled field:

```cpp
anchorUnitDirection
rotationRadians
width / height
cellSizeMeters
samples[]
```

External image/GIS importers can convert data into this project-authority representation. Runtime sampling is bilinear and seam-independent. M04 does not defer raster behavior to a placeholder renderer texture.

## 8. Material validation

`ReferencesKnownMaterials()` checks every authored material constraint against the M02 `GeologicalMaterialLibrary`.

The invariant remains:

> material constraints choose where authored substrate intent applies; M02 geological materials define what that substrate physically is.

## 9. Project-authority codec

M04 adds `.orbitterrainconstraints` TOML assets through:

```cpp
ParseTerrainConstraintSetToml()
SerializeTerrainConstraintSetToml()
LoadTerrainConstraintSetFile()
```

All six field arrays and all five primitive kinds serialize through the same format. The serialized file contains authored records only; derived terrain samples, generated height pages and cache residency are never serialized as authority.

## 10. Acceptance coverage

`Orbit.TerrainAuthoredConstraints` verifies:

- a spline-authored canyon modifies derived height;
- terrain outside spline falloff remains unchanged;
- a protection field permits partial erosion rather than freezing the canyon;
- drainage can reuse the same spline geometry;
- material constraints coexist in the same unified set;
- serialize → parse → regenerate reproduces the canyon without persisting generated terrain;
- point, brush, polygon and raster primitives execute real evaluators;
- Add/Subtract/Multiply/Min/Max/Replace composition is deterministic;
- the same physical point represented through +X and +Z cube faces receives identical authored influence.

The isolated `Orbit V0.0.4 Terrain` Windows lane passed CMake configure, compilation of the M00–M04 contract targets, and the filtered CTest suite including `Orbit.TerrainAuthoredConstraints`.

## 11. M04 invariants

1. **Constraints are project authority; resulting terrain is derived.**
2. **All terrain authoring geometry is canonical body-space or canonical tangent-space, never face-local procedural coordinates.**
3. **Height, gradient, uplift, material, protection and drainage remain independent fields.**
4. **Protection modifies process allowance; it does not implicitly disable terrain processes.**
5. **Material constraints reference M02 rock identity and cannot redefine rock physics.**
6. **Spline-authored terrain survives regeneration because the spline/constraint records are persisted, not because a generated heightmap is preserved.**

## 12. Next boundary
