# Orbit V0.0.3 — M20A World & Celestial Authoring

Status: **Partial — permanent project/world/session/runtime backend implemented; visible Studio integration remains**

Branch target: `orbit`

This document is a normative extension of `docs/V0.0.3_SPEC.md`. It inserts a focused
world-authoring milestone between M20 and M21 without renumbering the existing build,
platform and integration milestones.

The reason for M20A is architectural rather than cosmetic: Orbit already has the permanent
Studio shell, schema/property system, commands/transactions, Explorer, Properties, plugins,
RPC/MCP and celestial runtime primitives, but the original milestone sequence did not give
the user-facing creation and configuration of a world/system/body hierarchy its own
acceptance gate.

M20A closes that gap. It does not introduce a second editor-only world model. The SQLite
semantic hierarchy remains authority and the active runtime universe/frame graph remains a
derived runtime representation of that authority.

---

## 1. Authoring experience

Orbit Studio should support world setup through the same contextual interaction style used
throughout the editor rather than through one large modal wizard.

The intended hierarchy is:

```text
Project
  World
    Celestial System
      Celestial Body
        real capability records
        authored systems and semantic children
        path networks
```

Selecting an object exposes only commands and properties that apply to that semantic type.
Examples:

- select a `World` -> create a celestial system or body;
- select a `Celestial System` -> create a body;
- select a `Celestial Body` -> edit its real shape/mass/frame/rotation properties or attach
  a registered runtime-backed capability;
- select two path nodes -> existing path connection commands appear;
- select a material-compatible object -> material operations appear.

World authoring must therefore remain an application of the shared schema and command
registries rather than a hand-coded parallel panel.

---

## 2. Permanent authority and residency rules

M20A follows the existing V0.0.3 invariants:

- `Project.orbit.toml` is project authority;
- `.orbitworld` SQLite documents are semantic world authority;
- world/system/body/capability records and authorable properties are CPU semantic data;
- the frame graph, `BodyRegistry` and runtime capability registries are derived runtime
  representations reconstructed from semantic authority;
- render resources, previews, terrain meshes and other generated products remain derived;
- Studio, plugins and MCP invoke the same commands;
- every semantic authoring operation is transactional and undoable;
- no UI control is added for a capability that has no real runtime semantics yet.

Atmosphere, hydrosphere and climate UI must be added only when their semantic records have
real owners and can be applied to corresponding runtime services. M20A must not use
decorative booleans to pretend those systems are authored.

## 3. Production slices implemented

### 3.1 Semantic types

The built-in schema catalog contains the M20A world authority types:

- `World`;
- `Celestial System`;
- `Celestial Body`;
- `Terrain Surface` as the first real runtime-backed body capability.

Additional forward surface asset identities may exist for later milestones, but they are not
presented as implemented runtime capabilities until their runtime owners exist.

### 3.2 Runtime-backed body properties

The `Celestial Body` schema exposes properties that map directly onto the current universe
and frame model:

- sphere versus ellipsoid shape intent;
- equatorial/reference radius;
- polar radius;
- mass;
- position in the parent frame;
- rotation period;
- axial tilt;
- rotation phase at the system epoch;
- material assignment.

These are ordinary schema properties, so Properties, persistence validation, plugins and
RPC/MCP schema discovery observe the same definitions.

### 3.3 Transactional creation commands

The shared command registry contains:

- `Create Celestial System`;
- `Create Celestial Body`;
- `Create Terrain Surface`;
- `Remove Terrain Surface`.

`Create Celestial System` is enabled when exactly one `World` is selected.

`Create Celestial Body` is enabled when one `World` or one `Celestial System` is selected.
When invoked on a world with no system, the command creates the first system and body inside
one transaction. The entire edit is therefore one undo unit.

`Create Terrain Surface` is enabled only for one selected spherical `Celestial Body` that
does not already own that capability. It creates the semantic terrain recipe and its complete
implemented analytic-terrain parameters in one transaction. `Remove Terrain Surface` uses
the same command/undo path and restores the same stable capability object ID and explicit
properties on undo.

The newly created semantic object becomes the shared editor selection.

### 3.4 Metadata-driven contextual command surfaces

Commands may declare stable presentation targets such as:

```text
explorer.context
properties.toolbar
viewport.toolbar
viewport.radial
```

`CommandSurfaceRegistry` merges these declarations with explicitly configured surface slots.
Metadata-contributed contextual commands are only presented when their live enable predicate
applies. This removes the requirement to add every new authoring operation manually to
`OrbitStudio` composition code.

World and terrain-capability commands contribute to:

```text
explorer.context
properties.toolbar
```

As a result, the existing Explorer context menu and Properties toolbar can expose world
authoring operations without owning their mutation implementation.

### 3.5 Automation

The commands are normal automation-visible `CommandRegistry` entries. They are therefore
present in the structured command catalog and can be invoked through the same RPC/MCP
command path used by Studio.

The transport-independent RPC layer also exposes project/world/body convenience methods,
including real capability discovery and mutation, while delegating mutations to
`ProjectDocument` or shared commands rather than implementing a parallel editor API.

### 3.6 Regression coverage

Regression coverage now exercises the real semantic workflow:

- richer celestial schemas;
- world selection -> system creation;
- system selection -> body creation;
- persistent World -> System -> Body hierarchy;
- body radius, mass, parent-frame position, rotation and tilt visibility in Properties;
- multi-object body-property editing;
- hierarchy rename/reparent;
- terrain capability create/remove and property persistence;
- undo/redo behavior;
- semantic terrain recipe -> `AnalyticTerrainSource` -> `SurfaceRegistry` composition;
- live runtime capability rebuild after a recipe edit;
- stable runtime body IDs and stable semantic capability IDs across undo/reopen;
- explicit rejection of unsupported ellipsoid analytic terrain instead of approximation.

### 3.7 Multi-world project authority

`ProjectDocument` owns the project-level multi-world API instead of leaving world management
to ad-hoc UI code.

Implemented:

- `WorldPaths()` recursively enumerates authoritative `.orbitworld` documents in stable
  lexical order;
- persistent `WorldDescriptor` identity/display/schema/startup metadata;
- `CreateWorld()` safely creates another versioned SQLite world below `Worlds/` and refuses
  overwrite/path escape;
- `SetWorldDisplayName()` edits persistent document display metadata;
- `SetStartupWorld()` validates an existing project-owned world and atomically persists the
  startup-world choice;
- document tests cover nested discovery, creation, duplicate rejection, path validation,
  startup-world persistence and reopen.

No Studio-owned project-world catalog is permitted.

### 3.8 Transactional world/session ownership

`EditorWorldSession` now owns every service whose lifetime is scoped to one active
`.orbitworld` document:

```text
WorldDatabase
SchemaRegistry
ObjectStore
SelectionService
CommandService + CommandRegistry
Explorer + Inspector
CommandSurfaceRegistry
PluginManager
UniverseComposition
SurfaceComposition
```

A world switch constructs and validates a complete candidate state before checkpointing and
replacing the current world. Failed opens leave the active session intact, and switching is
blocked while an authoring transaction is active.

World-bound facades and plugins are destroyed with their world state, so they cannot retain
references into a previous world after a hot switch.

### 3.9 Semantic-to-runtime universe and surface composition

`UniverseComposition` reconstructs `FrameGraph + BodyRegistry` directly from semantic
System/Body authority. Runtime system/body/frame IDs are deterministically derived from
stable semantic object IDs and therefore survive close/reopen.

`SurfaceComposition` reconstructs real body surface capabilities from semantic capability
children. The implemented `Terrain Surface` record produces an `AnalyticTerrainSource`
attached through `SurfaceRegistry` to the composed runtime body. Because `SurfaceRegistry`
references the active `BodyRegistry`, it is invalidated and rebuilt whenever universe
composition changes; it can never retain a dangling previous-universe registry.

`EditorWorldSession::RefreshUniverseIfChanged()` refreshes universe and surface composition
from the same semantic revision. Regression coverage proves terrain recipe edits affect the
live runtime source in the same session.

### 3.10 Studio composition and project lifecycle backend

`StudioSession` is the application-facing composition root for one project. It owns:

- `EditorWorldSession`;
- authoritative World Documents model;
- active-body model;
- per-view target registry;
- session-aware RPC host.

`StudioWorkspace` owns the active `ProjectDocument + StudioSession`. New/Open Project build a
complete candidate project/session before replacing the current workspace. Failed opens keep
the active project intact; close/move paths checkpoint dirty authority first.

`StudioWorkspaceRpcHost` keeps a stable dispatcher across `project.create`, `project.open`
and `project.close`, then delegates ordinary world/object/build/view RPC into the currently
active project session.

### 3.11 Active body and independent viewport targets

`ActiveBodyModel` resolves semantic selection/focus to the corresponding composed runtime
body/frame and invalidates on world-session generation changes.

`ViewportTargetRegistry` supports multiple independent views. Each view can either follow the
shared active body or remain pinned to another semantic body. Runtime IDs are always
reconstructed from semantic authority rather than persisted in viewport state.

The same targeting state is exposed through structured RPC (`view.*`). Visible creation and
layout of multiple RenderViews in the current `OrbitStudio` application remains pending.

### M20A.5 — Real capability authoring

Implemented real capability:

- `surface.terrain` / semantic `Terrain Surface`;
- CPU semantic recipe authority;
- runtime owner `SurfaceRegistry`;
- implementation `AnalyticTerrainSource`;

### M20A.6 — Procedural world setup and diagnostics

The implemented terrain capability exposes real seed and analytic terrain recipe properties

Remaining visible/derived diagnostics include:

- climate inputs;
- biome inputs;
- procedural dependency status;
- rebuild/invalidation state;
- elevation/geology/hydrology/climate/biome/buildability debug views;
- validation errors and resource diagnostics.

The UI requests builds through the procedural graph. It never runs generator implementation
logic directly from a widget.

## 5. M20A acceptance criteria

M20A is complete when all of the following are true:

1. A user can create or open a project from Orbit Studio without relying on a command-line
   manifest argument or the scratch-project fallback.
2. A project can contain and manage multiple versioned world documents from Studio.
3. A blank world can be populated with a celestial system and multiple bodies entirely
   through Studio contextual actions.
4. The same creation operations can be driven through RPC/MCP and plugins.
5. Created objects persist, reopen with stable IDs and participate in undo/redo.
6. Body shape, size, mass, parent-frame position and rotation settings reconstruct the real
   `FrameGraph`/`BodyRegistry` representation.
7. Editing those settings updates the active runtime preview in the same session.
8. Sphere and ellipsoid bodies are previewed from their authored values rather than from
   hard-coded application defaults.
9. Studio can target different bodies/frames from independent resizable RenderViews.
10. Capability controls appear only for real registered capability implementations; no fake
    future-feature toggles are accepted.
11. Deleting derived caches does not remove any world-authoring authority.
12. The integration proof can reopen the project and reconstruct the same universe solely
    from project/world source documents.

## 7. Architectural acceptance rule

A new world-setup control is acceptable only if the complete path exists:

```text
Studio / Plugin / MCP
        ↓
shared command + validation
        ↓
transaction or project-document atomic mutation
        ↓
authoritative semantic document
        ↓
runtime composition/invalidation
        ↓
derived preview/render state
```

If a proposed control cannot currently reach a real authoritative owner and runtime
consumer, it stays out of the editor until that path is implemented.
