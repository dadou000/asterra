# Orbit V0.0.3 — M20A World & Celestial Authoring

Status: **Partial — semantic authoring + multi-world backend implemented**

Branch target: `orbit`

This document is a normative extension of `docs/V0.0.3_SPEC.md`. It inserts a focused
world-authoring milestone between M20 and M21 without renumbering the existing build,
platform and integration milestones.

The reason for M20A is architectural rather than cosmetic: Orbit already has the permanent
Studio shell, schema/property system, commands/transactions, Explorer, Properties, plugins,
RPC/MCP and celestial runtime primitives, but the original milestone sequence did not give
the user-facing creation and configuration of a world/system/body hierarchy its own
acceptance gate.

M20A closes that gap. It does not introduce a second editor-only world model. The SQLite
semantic hierarchy remains authority and the active runtime universe/frame graph remains a
derived runtime representation of that authority.

---

## 1. Authoring experience

Orbit Studio should support world setup through the same contextual interaction style used
throughout the editor rather than through one large modal wizard.

The intended hierarchy is:

```text
Project
  World
    Celestial System
      Celestial Body
        authored systems and semantic children
        path networks
        future real capability records
```

Selecting an object exposes only commands and properties that apply to that semantic type.
Examples:

- select a `World` -> create a celestial system or body;
- select a `Celestial System` -> create a body;
- select a `Celestial Body` -> edit its real shape/mass/frame/rotation properties;
- select two path nodes -> existing path connection commands appear;
- select a material-compatible object -> material operations appear.

World authoring must therefore remain an application of the shared schema and command
registries rather than a hand-coded parallel panel.

---

## 2. Permanent authority and residency rules

M20A follows the existing V0.0.3 invariants:

- `Project.orbit.toml` is project authority;
- `.orbitworld` SQLite documents are semantic world authority;
- world/system/body records and authorable properties are CPU semantic data;
- the frame graph and `BodyRegistry` are active runtime representations reconstructed from
  semantic authority;
- render resources, previews, terrain meshes and other generated products remain derived;
- Studio, plugins and MCP invoke the same commands;
- every semantic authoring operation is transactional and undoable;
- no UI control is added for a capability that has no real runtime semantics yet.

Atmosphere, hydrosphere, climate and terrain-generator UI must be added only when their
semantic records have real owners and can be applied to corresponding runtime services.
M20A must not use decorative booleans to pretend those systems are authored.

## 3. Production slices implemented

### 3.1 Semantic types

The built-in schema catalog contains:

- `World`;
- `Celestial System`;
- `Celestial Body`.

### 3.2 Runtime-backed body properties

The `Celestial Body` schema exposes properties that map directly onto the current universe
and frame model:

- sphere versus ellipsoid shape intent;
- equatorial/reference radius;
- polar radius;
- mass;
- position in the parent frame;
- rotation period;
- axial tilt;
- rotation phase at the system epoch;
- material assignment.

These are ordinary schema properties, so Properties, persistence validation, plugins and
RPC/MCP schema discovery observe the same definitions.

### 3.3 Transactional creation commands

The shared command registry contains:

- `Create Celestial System`;
- `Create Celestial Body`.

`Create Celestial System` is enabled when exactly one `World` is selected.

`Create Celestial Body` is enabled when one `World` or one `Celestial System` is selected.
When invoked on a world with no system, the command creates the first system and body inside
one transaction. The entire edit is therefore one undo unit.

The newly created semantic object becomes the shared editor selection.

### 3.4 Metadata-driven contextual command surfaces

Commands may declare stable presentation targets such as:

```text
explorer.context
properties.toolbar
viewport.toolbar
viewport.radial
```

`CommandSurfaceRegistry` merges these declarations with explicitly configured surface slots.
Metadata-contributed contextual commands are only presented when their live enable predicate
applies. This removes the requirement to add every new authoring operation manually to
`OrbitStudio` composition code.

The world creation commands contribute to:

```text
explorer.context
properties.toolbar
```

As a result, the existing Explorer context menu and Properties toolbar expose world
authoring operations without owning their mutation implementation.

### 3.5 Automation

The commands are normal automation-visible `CommandRegistry` entries. They are therefore
present in the structured command catalog and can be invoked through the same RPC/MCP
command path used by Studio.

### 3.6 Regression coverage

Editor-model regression coverage now exercises the real semantic workflow:

- richer celestial schemas;
- world selection -> system creation;
- system selection -> body creation;
- persistent World -> System -> Body hierarchy;
- body radius, mass, parent-frame position, rotation and tilt visibility in Properties;
- multi-object body-property editing;
- hierarchy rename/reparent;
- undo/redo behavior.

### 3.7 Multi-world project authority

`ProjectDocument` now owns a production project-level multi-world API instead of leaving
world management entirely to ad-hoc UI code.

Implemented:

- `WorldPaths()` enumerates authoritative `.orbitworld` documents in stable lexical order;
- `CreateWorld()` safely creates another versioned SQLite world below `Worlds/` and refuses
  overwrite;
- `SetStartupWorld()` validates an existing project-owned world and atomically persists the
  startup-world choice;
- world display metadata is initialized when a world is created;
- document tests cover world discovery, creation, duplicate rejection, path-escape
  rejection, startup-world persistence and reopen.

This is the permanent backend used by the future project browser and World Documents panel.
The UI must not invent a separate project-world catalog.

## 4. Remaining M20A deliverables

### M20A.1 — Project Browser

Deliver:

- New Project;
- Open Project;
- Recent Projects;
- Close Project;
- Project Settings;
- startup-world selection.

Project creation must call `ProjectDocument::Create`; project opening must call
`ProjectDocument::Open`. Studio must not maintain a second project format.

### M20A.2 — World Documents panel and active-world lifecycle

The backend world catalog/create/startup operations are implemented. Remaining Studio work:

- dockable world list;
- create-world UI using `ProjectDocument::CreateWorld`;
- change-startup UI using `ProjectDocument::SetStartupWorld`;
- world display-name editing;
- active authoring-world open/close/switch;
- schema/migration validation feedback;
- current file path and stable world ID display.

Hot active-world switching must recompose the owning editor session rather than rebinding a
set of scattered references in-place.

### M20A.3 — Semantic-to-runtime universe composition

Deliver a reusable composition layer that rebuilds or incrementally synchronizes:

```text
World semantic records
        ↓
Celestial System records
        ↓
Celestial Body records
        ↓
FrameGraph + BodyRegistry
```

It must consume the exact persisted body properties described above. Studio must stop
hard-coding a single `Helion` system and a single first body as its universe composition.

Acceptance requires body creation/property edits to affect the active preview in the same
Studio session without reopening the project.

### M20A.4 — Active body and viewport targeting

Deliver:

- active body follows semantic selection/focus;
- focus selected body;
- body/frame picker per RenderView;
- at least two simultaneous resizable views;
- perspective and body-map/debug view composition.

No global singleton viewport is introduced.

### M20A.5 — Real capability authoring

As real semantic/runtime capability services become available, add schema-backed capability
records for:

- surface/terrain;
- atmosphere;
- hydrosphere;
- field sets;
- climate/procedural graph inputs.

Each capability must define authority, runtime owner, CPU/GPU residency, invalidation and
persistence before its Studio controls are added.

### M20A.6 — Procedural world setup and diagnostics

Once the corresponding real services are integrated, Studio should expose contextual world
setup for:

- terrain recipe/seed and global shape inputs;
- hydrology and erosion dependencies;
- climate inputs;
- biome inputs;
- procedural dependency status;
- rebuild/invalidation state;
- elevation/geology/hydrology/climate/biome/buildability debug views;
- validation errors and resource diagnostics.

The UI requests builds through the procedural graph. It never runs generator implementation
logic directly from a widget.

### M20A.7 — Dedicated world automation convenience methods

Generic command discovery/invocation is already valid for system/body creation. Add explicit
RPC/MCP convenience domains without creating a parallel mutation implementation:

```text
world.list
world.create
world.open
world.close
world.set_startup

body.list
body.create
body.capabilities
body.set_capability
```

These methods must delegate to `ProjectDocument`, schemas and the shared command registry.

## 5. M20A acceptance criteria

M20A is complete when all of the following are true:

1. A user can create or open a project from Orbit Studio without relying on a command-line
   manifest argument or the scratch-project fallback.
2. A project can contain and manage multiple versioned world documents from Studio.
3. A blank world can be populated with a celestial system and multiple bodies entirely
   through Studio contextual actions.
4. The same creation operations can be driven through RPC/MCP and plugins.
5. Created objects persist, reopen with stable IDs and participate in undo/redo.
6. Body shape, size, mass, parent-frame position and rotation settings reconstruct the real
   `FrameGraph`/`BodyRegistry` representation.
7. Editing those settings updates the active runtime preview in the same session.
8. Sphere and ellipsoid bodies are previewed from their authored values rather than from
   hard-coded application defaults.
9. Studio can target different bodies/frames from independent resizable RenderViews.
10. Capability controls appear only for real registered capability implementations; no fake
    future-feature toggles are accepted.
11. Deleting derived caches does not remove any world-authoring authority.
12. The integration proof can reopen the project and reconstruct the same universe solely
    from project/world source documents.

## 7. Architectural acceptance rule

A new world-setup control is acceptable only if the complete path exists:

```text
Studio / Plugin / MCP
        ↓
shared command + validation
        ↓
transaction or project-document atomic mutation
        ↓
authoritative semantic document
        ↓
runtime composition/invalidation
        ↓
derived preview/render state
```

If a proposed control cannot currently reach a real authoritative owner and runtime
consumer, it stays out of the editor until that path is implemented.
